## 0. 文档说明

> 最新工程决策：本项目从未正式生产上线，因此数据和运行时只采用未来最优契约。旧 001～025 开发迁移已被单一绿色基线 001 替代；所有环境只通过 Alembic 建库，应用运行时禁止 `create_all`。新 Task 必须显式绑定 TargetAccount；除企业名称外的消歧字段仍全部非必填。Skill 不保留旧 `template_id`、维度配置或 Harness 的兼容执行分支。

### 0.1 文档目的

本文档用于将当前“一次性生成潜在需求分析报告”的系统，升级为覆盖以下完整闭环的 AI 售前商机研究与作战工作台：

1. 用户可围绕已生成报告继续与智能体讨论、补充研究和修订报告。
2. Skill 从简单维度配置升级为基于 `SKILL.md` 的专家工作流，并支持两层级 Skill、可视化编辑，以及 v3.5 的 GitHub/离线导入。
3. 批量上传提供标准化模板，降低输入错误率，提高批量任务创建效率。
4. 用户可维护多个企业能力档案及多个产品，系统能够仅根据目标企业名称自动发现需求并匹配我方产品。
5. 将研究结果沉淀为可验证的 Claim、商机假设和下一步行动，而不是止步于报告内容。
6. 增加客户私有证据、目标企业主数据与消歧、客户雷达、业务结果反馈等支撑能力。
7. 智能体在执行前或执行中遇到会实质影响研究范围、事实判断或报告质量的不确定性时，主动暂停并请求用户澄清，确认后再继续执行。
8. 建立分层上下文治理与可回溯压缩，在长会话、长报告和多轮研究下控制成本与信息噪声，同时保证关键事实、反证、澄清回答和引用不丢失。
9. 在证据审计与报告/评分之间建设 Opportunity Intelligence Gate，可靠区分历史相关、已有能力、当前缺口、介入窗口和暂无商机。
10. 将多小时单体任务升级为可暂停、可恢复、可审计的耐久短工作单元，避免重复投递、重复模型调用、假进度和 Redis-only 恢复。

本文档既是专家评审输入，也是后续详细设计、研发 WBS、测试计划和验收方案的上位需求依据。

### 0.2 已确认且不再重复讨论的产品决策

1. 智能体不得直接覆盖正式报告。报告修改必须经过“生成草案—展示差异—用户确认—生成新版本”。
2. 一个默认 Workspace 可以维护多个企业能力档案，每个档案可维护多个产品线、产品、解决方案、案例和资质。
3. 本项目 Skill 统一采用 Codex/Claude 风格的 `SKILL.md` 目录标准。
4. Skill 上层必须保留面向普通用户的可视化编辑界面。
5. 目标企业只有“企业名称”为必填字段，官网、信用代码、地区、行业等消歧字段均为非必填项。
6. 不支持运行时双格式兼容。外部 Skill 在导入时一次性转换成本项目标准格式。
7. 本路线任何阶段都不执行来自外部 Skill 的任意代码。
8. 智能体不得静默补全会影响结论的关键未知信息；必须通过可审计的澄清请求获得用户确认，或由用户明确授权按已展示的假设继续。
9. 即使模型支持 1M 上下文，也不默认把全部历史和原始材料直接发送给 LLM；原始资产永久保持可回溯，压缩结果只能作为带来源的派生上下文。
10. 商机评分必须在商机裁决之后执行；旧的证据相关度评分不得继续作为正式商机结论的回退路径。
11. PostgreSQL 是任务状态、工作单元、外部调用、预算账本、事件和恢复位置的唯一事实源；Redis 只承担队列、快速协调和缓存，不再作为恢复正确性的唯一依据。
12. Celery 消息只承载可重入短工作单元；任务暂停、恢复、取消和终态必须经过耐久状态机，不允许 Agent 直接写全局任务状态。
13. Token 与费用预算只用于估算、告警和审计，不在执行中自动阻断模型调用或降低强制质量门；高成本补充研究可以在创建前请求确认。
14. `PARTIAL` 不是默认成功。只有达到对应 Skill 已批准的最低交付物、引用和强制审计要求时，才允许展示或导出部分结果。
15. 候选筛选在机器质量门未通过前只能旁路影子运行，不能改变用户候选集、抓取、提取、OIG 输入或最终报告。

#### 0.5.0a 长耗时优化对本次升级的路线调整

本轮优化的核心结论不是“所有任务已经足够快”，而是“长任务已具备可恢复、可观测、可控制的开发基线”。20/50 任务压测通过说明该基线可以作为后续架构输入；100 任务由业务方取消，不能被写成容量通过证据。候选筛选的机器质量门仍未通过，因此也不能把影子筛选带来的调用量变化计入业务提效承诺。

| 工作类型 | 开发准入 | 试点/生产准入 | 本版本规则 |
| --- | --- | --- | --- |
| 纯领域数据、查询、版本与会话能力 | 可在当前耐久开发基线上继续实施，并完成隔离测试 | 需同时通过 P0-13 与 TEO-Release | 只能读写新领域对象；不得重新接入旧 WebSocket、Redis Checkpoint 或旧 Harness 状态 |
| 会触发长运行的补充研究、执行中澄清与自动商机运行 | 仅可接入 `execution/` 短 WorkUnit、租约、Outbox 和持久事件；先做 Mock/隔离验证 | TEO-Release 书面 Go 后才可面向试点开启 | 等待用户回答期间不得创建外部调用；恢复必须使用 `control_version` 和幂等键 |
| 候选筛选、批处理降耗策略 | 仅影子、可审计、不得影响用户结果 | 重新通过 G1 后另行授权 | 不得进入 Candidate、Evidence、Claim、OIG、评分或正式报告 |
| 报告/商机业务体验 | 可开发 UI 与只读展示 | 未经上述门禁不得标记为“可用试点”或宣称提速 | 所有业务结论仍受 Claim、证据域和 OIG 约束 |

因此，后续排期改为双轨：**TEO-Release** 独立完成首次部署演练和生产 Go/No-Go；**v3.2 开发轨**继续完成不依赖生产外部调用的领域数据、版本、会话和上下文能力。两条轨道在“补充研究试点、执行中澄清、自动商机运行”处汇合，未汇合前不得开展真实试点。

#### 0.5.0a-1 长耗时优化的运行时收口要求

抓取与提取的运行时收口已完成开发验证：抓取使用 `FETCH_PLAN → FETCH_BATCH×N → FETCH_COMPLETE`，每批可独立重试与恢复；提取只在前一批完成并计算充分性后才派发下一批，满足早停时以 `EXTRACTION_COMPLETE` 结束该维度。该结果不等于端到端性能目标已达成，以下要求仍是 v3.2 试点前的共同门禁：

1. 抓取批次必须持续保持输入哈希、幂等和网络硬截止；单个 URL 的重试不得阻塞其他抓取批次。
2. 提取调度必须持续保持“前一批完成后才决定下一批”的语义；早停必须能减少后续外部调用，而不仅是写入事件。
3. 任何并行化必须保留 Provider 限流、租约 fencing、暂停后零新增调用、失败隔离和持久调用账本；不得以提高 Worker 并发替代上述控制。
4. 1M 上下文候选筛选继续维持影子模式。G1 未重评通过前，不能用其结果减少抓取、提取、Evidence、Claim、OIG 或报告输入。
5. “P90 ≤40 分钟/≤20 分钟”仍只是发布验收目标；只有使用真实业务形态、记录查询数、候选数、抓取批数、提取批数、外部调用和 Token 的端到端验收，才可宣称达成。

#### 0.5.0b 最新整合：OIG 不得重新放大长任务

本次长任务优化同时改变商机判断的实现边界。OIG 是业务裁决层，不是为每条 Evidence、每个合同或每项政策各运行一次大模型的并行分析器；否则即使耐久执行可恢复，也会重新产生“候选数量 × 串行模型调用”的小时级任务。

| OIG 层次 | 允许的实现 | 禁止的实现 | 失败或信息不足时的动作 |
| --- | --- | --- | --- |
| 时间、采购生命周期、硬门槛 | 基于已归一化字段的确定性服务、状态机和可回放规则 | 为每条历史招标再次调用模型判断是否截止 | 标记未知/冲突，创建补证或澄清，不提升裁决等级 |
| 能力、缺口、政策适用和反证 | 复用 Claim、三证据域、ContextManifest 与带来源快照；必要语义判断按批次短 WorkUnit 执行 | 将全部网页正文、整个会话或每条证据独立送入模型 | 记录未决因子和证据来源，限制 Gate 上限 |
| Gate、评分和报告 | 读取不可变 GateDecision；同一输入哈希复用已完成结果 | Gate 失败后调用旧评分器或用报告模型补写确定性结论 | 阻断正式商机结论，显示“裁决未完成/需补证” |

执行约束如下：

1. OIG 的确定性步骤必须先于任何语义模型调用运行，并在每个 WorkUnit 完成后持久化可复用的中间结果。
2. 必须以 `analysis_as_of_date`、Claim/证据版本、Skill 版本和产品约束构成输入哈希；输入未变化时不得重复执行同一裁决。
3. 语义步骤只能消费最小充分的 L0～L3 工作集。L0、关键反证、用户澄清和数据授权超限时，应拆分、回填或请求澄清，不能静默截断。
4. 语义批处理的故障半径必须受短 WorkUnit 限制；不得以 OIG 名义恢复“逐条 Evidence 一次模型调用”或把全量原始网页塞入 1M 上下文。
5. 证据不足时，系统应先输出待验证因子，并在重大不确定性下进入 `WAITING_FOR_INPUT` 或创建耐久补证任务；不得用推测填满 Gate 因子。
6. 候选筛选的 G1 仍未通过，影子结果不能作为 OIG 的输入或用于缩减正式证据集。性能优化与业务结论必须分别验收。

#### 0.5.1 产品定位与当前形态

当前项目是一套面向售前顾问、解决方案经理和商机挖掘人员的 B/S 架构 AI 企业调研系统。系统以“目标企业名称 + 需求方向”为核心输入，通过搜索、网页抓取和多智能体分析，形成带证据索引的潜在需求分析报告。

当前主要使用流程为：

```text
创建目标企业调研任务
→ 创建耐久 Run 与短工作单元
→ 异步搜索、候选规范化、抓取与批次提取
→ 按多个维度进行智能体分析并持久化阶段资产
→ 汇总、审计并生成分析报告
→ 通过 SSE 查看真实进度；可暂停、继续、取消或查看 PARTIAL
→ 查看证据及报告
→ 导出 PDF / Word
```

项目采用 Next.js、FastAPI、PostgreSQL、Redis、Celery 和 Docker Compose，已经形成前后端分离、异步任务执行和本地部署的工程基础。

#### 0.5.4 当前最主要的产品缺口

1. 报告仍然是一次性结果，用户无法在原始研究上下文中继续追问、补证和修订。
2. Skill 有管理基础，但专业策略表达、组合编排、标准目录和评测体系不足。
3. 批量导入有接口与向导基础，但缺少稳定、易理解、可版本管理的上传模板。
4. 系统不了解用户企业自身的产品、方案与案例，无法自动完成“客户需求—我方能力”的匹配。
5. 目标企业仍主要依赖名称字符串，缺少统一主数据、同名主体识别和集团关系管理。
6. v3.1 多项功能尚未完成正式端到端验收，文档状态、迁移状态和真实运行状态需要在新版本开发前统一收口。
7. 研究结论没有统一 Claim 对象，也没有从需求信号到正式商机的验证阶段。
8. 客户访谈、RFP 和会议纪要等私有材料尚未形成独立、安全的证据域。
9. 能力、客户、Skill 和报告主要按个人使用设计，缺少稳定的 Workspace 资产归属。
10. 候选筛选三样本机器门禁仍为 `FAIL`；当前只能影子运行，尚未证明对用户任务的质量与耗时收益。
11. 耐久执行已通过开发与隔离验证，但首次生产部署仍为 No-Go，绿色基线、单路径 Worker 和 Relay 尚待部署/恢复演练与烟测。
12. 执行状态已经支持 `WAITING_FOR_INPUT`，但澄清问题/回答持久化、等待期零外部调用及回答后幂等恢复尚未完成。
13. 旧文档仍描述 Redis Checkpoint、WebSocket 假进度和 Token 熔断，必须以耐久执行状态机、SSE 和预算仅告警的新口径替换。

### 0.6 两位专家意见处理结论

本轮评审不采用“意见累加”方式，而按照业务价值、当前产品阶段、工程成本和既有产品决策进行筛选。

| 专家建议 | 处理结论 | 落地方式或不采纳原因 |
| --- | --- | --- |
| 增加信号、商机假设、正式商机和销售阶段 | 采纳 | 将产品主链路调整为“客户—信号—商机假设—验证—正式商机—行动推进” |
| 增加客户私有证据和 Claim Registry | 采纳 | v3.2 建设第三证据域、结论状态、有效期和冲突管理 |
| 增加下一步行动、决策链、资格判断、价值假设 | 采纳 | 下一步行动进入 v3.2；决策链、资格卡和价值假设进入 v3.4 |
| 增加竞争者实体和竞争作战卡 | 采纳 | v3.4 建设，覆盖竞品、现有供应商、自研、维持现状和延期不投 |
| 报告提供一页简报、商机卡、行动清单等多视图 | 采纳 | 同一研究资产生成多种业务视图，完整报告不再是唯一入口 |
| 引用和审计结果渐进式披露 | 采纳 | 首屏克制展示，点击或展开后查看来源、置信度、快照和审计详情 |
| 展示智能体当前状态 | 采纳但限制 | 展示规划、搜索、提取、审计等操作状态和可审计摘要，不展示模型隐藏思维链 |
| 云端模型测上限、本地模型保底 | 采纳但限制 | 保留灵活模型路由和基准评测；内部及客户私有数据只能进入获批模型路由，不默认上传云端 |
| Skill 沙盘和 Dry Run | 采纳但限制 | 展示编译计划、工具、数据域、预算和 Mock 结果；继续禁止执行外部任意代码 |
| RAG 意图路由和图数据库 | 部分采纳 | 采用结构化检索、全文检索和向量检索路由；现阶段不把图数据库设为必选依赖 |
| Workspace 归属模型 | 采纳 | 初期创建默认 Workspace，核心业务对象归属于 Workspace；复杂组织和 RBAC 仍不进入主线 |
| CRM/OA/企微协同 | 部分采纳 | v3.4 提供 CSV/JSON/Webhook 最小输出契约；实时多人协作、@、自动推送和完整 CRM 集成暂缓 |
| 商业价值与 ROI Dashboard | 部分采纳 | v3.5 展示漏斗、节省工时和已验证商机金额；未经销售或 CRM 确认的数据不得作为真实金额 |
| 指定 Apple 风格和轻拟物化视觉 | 不作为强制需求 | 采纳低认知负荷、清晰层级和证据域区分原则，不绑定特定品牌或短期视觉风格 |
| GitHub Skill 导入继续作为 v3.3 核心 | 调整优先级 | 标准 `SKILL.md`、两层 Skill 和小白 UI 保留在 v3.3；GitHub 直连、上游更新和高级编排后移至 v3.5 |

本次修订坚持用户已确认的四个升级方向，但把交付顺序由“横向同时建设多个平台”调整为“先纵向打通一个可验证的售前场景，再逐步平台化”。

## 1. 执行摘要

### 1.1 当前问题

当前系统已经具备多智能体研究、搜索抓取、证据落库、证据审计、商机评分、报告生成、批量任务和 Skill 管理等基础能力，但产品价值主要停留在“输入任务—等待执行—查看报告—导出报告”的一次性流程。

用户查看报告后通常会产生新的问题，例如：

- 为什么得出这一结论？
- 这个证据是否足够可信？
- 能否继续查最近两年的招标情况？
- 能否对某个竞争对手做更深分析？
- 能否把补充发现写回报告？
- 结合我公司的具体产品，应该用什么方案切入？

现有系统无法把报告、搜索词、原始搜索结果、证据、审计结果和后续问题组织成可持续研究上下文，导致用户必须离开系统，在其他 LLM 中重新粘贴材料。

与此同时，现有 Skill 虽然已经保存搜索关键词、信源策略、评分权重和报告模板等配置，但实际执行链主要只消费分析维度，尚未形成真正的专家研究策略。

### 1.2 升级后定位

> 将系统从“一次性 AI 报告生成器”升级为“围绕客户、商机假设、证据验证、我方能力和下一步行动持续工作的 AI 售前商机作战工作台”。

### 1.3 升级后核心价值

- 对用户：报告不再是终点，而是研究和销售行动的起点。
- 对销售：系统把需求信号转为可接受、可验证、可分配的商机假设和行动卡。
- 对售前：系统能结合我方产品形成客户切入建议、资格判断和竞争策略。
- 对专家：专业方法可以沉淀为可组合、可测试、可迭代的 Skill。
- 对管理者：研究过程、证据、商机阶段、行动结果和用户决策均可追溯。
- 对系统：通过客户验证、阶段推进、赢单/丢单和 Skill 评测形成质量改进闭环。

## 3. 产品愿景、目标与原则

### 3.1 产品愿景

让售前、解决方案和客户经营人员能够通过一个工作台完成：

```text
建立 Workspace 与我方能力
→ 输入目标客户
→ 发现需求信号并形成 Claim
→ 生成可验证的商机假设
→ 匹配产品、竞争策略和资格条件
→ 由销售接受并通过客户沟通验证
→ 生成下一步行动并推进销售阶段
→ 持续研究、复盘和监控客户变化
```

### 3.2 业务目标

| 目标编号 | 目标 |
| --- | --- |
| GOAL-01 | 用户无需离开系统即可完成报告后续问答、补充研究和报告修订 |
| GOAL-02 | 把专家研究方法沉淀为可组合、可测试、可导入的标准 Skill |
| GOAL-03 | 通过标准模板和逐行校验降低批量输入错误率 |
| GOAL-04 | 支持多企业能力档案和多产品管理，实现仅输入目标企业名称的商机线索发现和能力匹配 |
| GOAL-05 | 所有关键结论都能追溯到外部证据、客户私有证据或内部知识，且三者严格区分 |
| GOAL-06 | 区分需求信号、商机假设、客户确认事实和正式商机，避免把公开推断直接当成销售机会 |
| GOAL-07 | 将下一步动作、资格判断、竞争策略和阶段反馈沉淀为结构化业务对象 |
| GOAL-08 | 通过客户验证和阶段推进结果建立可复盘、可校准的商机经营过程 |

### 3.3 非目标

以下内容不属于 v3.2～v3.4 主线：

- SaaS 计费和套餐系统。
- 深度企业级多租户、复杂组织架构和团队协作空间。
- 完整 CRM 替代品。
- 自动向客户发送邮件、消息或投标材料。
- 实时多人共同编辑、@ 协作和自动推送到企微、钉钉等外部系统。
- 自动执行外部 Skill 中的 Python、JavaScript、Shell 等代码。
- 电话拨测、线下渠道、物理设备等重交互自动化。
- 将图数据库作为企业知识检索的必选技术依赖。
- 绑定 Apple 或其他特定品牌的视觉设计语言。
- 任意格式的运行时兼容层。

### 3.4 产品设计原则

1. **证据优先**：目标客户事实必须引用外部证据或经过授权的客户私有证据。
2. **三域分离**：外部公开事实、客户私有材料和我方内部能力不得相互代替证明。
3. **信号不等于商机**：公开事件只能形成信号或假设，正式商机必须经过销售接受和客户侧验证。
4. **用户确认**：正式报告、客户确认状态、商机阶段和关键业务决策不得由智能体静默修改。
5. **行动优先**：研究输出必须能转化为可验证、可分配的下一步行动，而不只生成更多内容。
6. **渐进式披露**：首屏降低认知负荷，普通用户使用向导，专家可进入证据与高级编辑。
7. **单一事实来源**：Skill 以标准目录为源，数据库不维护第二份手工配置。
8. **可回放**：任务、会话、研究分支、Claim、证据、商机阶段和版本均可追溯。
9. **安全导入与路由**：外部内容默认不可信；敏感数据只进入获批模型和工具路由。
10. **失败可解释**：数据不足、消歧失败、工具失败、预算终止和资格阻断必须明确显示。

## 4. 用户角色与核心场景

### 4.1 用户角色

| 角色 | 主要诉求 | 使用深度 |
| --- | --- | --- |
| 销售人员 | 快速判断客户是否值得跟进、如何开场 | 低到中 |
| 销售经理 | 查看商机假设漏斗、阶段推进、投入产出和团队采纳情况 | 中 |
| 售前顾问 | 深入分析需求、技术风险、竞争格局 | 中到高 |
| 解决方案经理 | 把客户需求映射到产品和方案 | 高 |
| 行业专家 | 沉淀行业研究策略和评估标准 | 高 |
| 产品管理员 | 管理企业能力档案、产品、案例和资料 | 中 |
| Skill 管理员 | 编辑、测试、发布和治理标准 Skill | 高 |
| 系统管理员 | 配置模型、搜索、预算、安全和数据保留 | 高 |

### 4.2 核心场景

#### 场景 A：围绕报告继续追问

用户查看报告后选中一条结论，询问依据、风险或替代解释。系统从报告、证据、原始搜索结果和审计结果中构建上下文并回答。

#### 场景 B：对报告发起补充研究

用户提出“继续查该企业近两年的数据治理招标”。系统创建子研究任务，新增研究资产和证据，完成后给出补充结论。

#### 场景 C：将讨论结果写回报告

智能体生成章节修改草案，用户查看 Diff，选择接受、部分接受或拒绝，接受后形成新报告版本。

#### 场景 D：专家构建两层 Skill

行业专家创建一级“政务智能客服商机研究”Skill，再组合企业识别、招标、政策、投诉、竞品和产品匹配等二级 Skill。

#### 场景 E：普通用户创建 Skill

用户通过可视化向导填写名称、适用场景、研究问题、信源、判断标准和报告结构，系统生成合规的标准 Skill 目录。

#### 场景 F：导入 GitHub Skill（v3.5）

用户提交 GitHub URL 和 Skill 目录。系统固定 Commit、执行安全检查、转换、预览和试运行，经用户确认后发布。

#### 场景 G：批量标准调研

用户下载标准模板，填写企业名称和需求方向，上传后完成字段映射、校验、Dry Run、成本确认和批量执行。

#### 场景 H：批量商机线索发现

用户选择一个企业能力档案，上传只包含企业名称的名单，系统逐行完成企业消歧、需求信号发现、产品匹配和商机假设生成。

#### 场景 I：仅输入目标企业名称

用户选择默认能力档案并输入目标企业名称。系统自动选择候选产品、Skill 和研究问题，输出可由销售接受或拒绝的商机假设，而不是直接创建正式商机。

#### 场景 J：上传客户私有材料

销售上传经过授权的会议纪要、RFP 或客户需求文档。系统将其归入客户私有证据域，提取 Claim 草案并等待用户确认，且不会把内容发送给搜索 Provider。

#### 场景 K：接受商机假设并执行下一步行动

销售查看信号、支持证据、反向证据和产品候选，接受或拒绝商机假设；接受后生成带负责人、日期和验证目标的下一步行动。

#### 场景 L：维护售前作战信息

售前在同一客户工作台中维护利益相关者、资格卡、竞争作战卡和价值假设，明确哪些内容来自公开推断、销售判断或客户确认。

#### 场景 M：历史采购与当前商机裁决

系统发现历史招标后，不直接生成当前商机，而是继续查找中标、合同、投产和维保信息，建立客户能力基线，判断合同续约/扩容/替换窗口，再输出 G1 历史能力、G2 待验证缺口、G3 当前信号、G4 潜在窗口、G5 可介入候选或 GX 暂无明确商机。

#### 场景 N：长任务暂停、恢复与部分交付

用户在多维研究过程中查看真实工作单元进度并发起暂停。系统完成当前不可中断外部调用后进入 PAUSED，不再创建新调用；恢复时从 PostgreSQL 中下一个未完成工作单元继续。若外部依赖不可恢复，只有满足 Skill 最低交付物、引用和强制审计要求时才允许形成明确 PARTIAL，否则任务失败并展示续研建议。

### 6.3 耐久执行与研究能力边界

```text
API / Batch / FollowUpResearch
→ execution 状态机与命令服务
→ TaskRun + 可重入短 WorkUnit DAG
→ Agent / LLM / Search / Fetch 领域处理器
→ 资产、事件和 Outbox 同事务持久化
→ SSE / Query Service 向用户展示
```

- `backend/app/execution/` 拥有任务状态、工作单元、租约、恢复、预算账本、事件和 Outbox。
- Agent/Harness 只负责研究语义和局部计算，不得直接写 Task 全局状态或自行实现恢复。
- Celery 消息只包含 task/run/unit 标识，Worker 必须回读数据库；同一 `unit_key` 重投不能产生重复 Evidence、Report、Audit 或费用结算。
- Redis 只用于消息队列、Provider 信号量、通知和缓存；清空 Redis 后仍应能从 PostgreSQL 对账恢复。
- 候选筛选、批提取和早停均必须受独立质量门控制。影子输出不进入报告、Claim、OIG 或产品匹配。

## 7. 目标企业主数据与消歧

### 7.1 建设目标

解决同名企业、简称、集团与子公司、品牌名与法人主体混淆问题，同时保持低门槛：用户只输入企业名称也能创建任务。

### 7.2 字段定义

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| 企业名称 | 是 | 用户输入的目标企业名称 |
| 官方名称 | 否 | 系统识别或用户确认的工商/公开正式名称 |
| 企业官网 | 否 | 提高消歧置信度 |
| 统一社会信用代码 | 否 | 强唯一标识 |
| 地区 | 否 | 省、市或国家/地区 |
| 行业 | 否 | 用户填写或系统识别 |
| 股票代码 | 否 | 上市公司可填写 |
| 所属集团 | 否 | 集团关系 |
| 企业别名 | 否 | 简称、品牌名、历史名称 |
| 用户备注 | 否 | 已知线索和业务说明 |

### 7.3 功能需求

#### FR-TGT-001 创建目标企业

- 用户仅填写企业名称即可保存和创建任务。
- 可选字段为空不得阻止任务创建。
- 用户可以在后续补充和修正字段。

#### FR-TGT-002 自动消歧

- 系统基于名称、地区、行业、官网、公开资料和集团关系生成候选企业。
- 每个候选项提供匹配依据和置信度。
- 高置信度可自动确认，但必须保留识别记录。
- 中置信度在正式研究前优先请用户选择候选项；用户也可确认按原始名称继续。
- 低置信度提示用户补充任意一个可选字段，但补充字段始终不是继续研究的强制条件。

建议阈值：

| 等级 | 建议置信度 | 系统行为 |
| --- | --- | --- |
| 高 | ≥0.85 | 自动确认并提示 |
| 中 | 0.55～0.84 | 展示候选，用户选择候选或确认按原始名称继续 |
| 低 | <0.55 | 提示补充信息；用户仍可选择“以未确认主体继续” |

阈值应支持后台配置和后续评测调整。

若用户选择“以未确认主体继续”，系统必须在任务页、报告标题区和事实引用处持续展示主体未确认标识，不得把推测主体写成已确认事实。由此确保官网、信用代码、地区、行业等字段在任何情况下均保持非必填。

#### FR-TGT-003 集团与子公司范围

- 用户可选择“仅研究当前主体”“包含子公司”“包含集团”。
- 默认仅研究已确认主体。
- 报告引用子公司或集团证据时必须标注主体关系。

#### FR-TGT-004 批量消歧

- 批量任务逐行消歧。
- 某一行需要人工确认时，仅暂停该行，不阻塞其他行。
- 批次详情显示待确认、已确认、低置信度、冲突四种状态。

### 7.4 验收标准

- 只填写企业名称可正常创建研究任务。
- 同名企业至少展示名称、地区、行业、官网等区分信息。
- 用户确认候选后，后续所有研究资产绑定统一 `target_account_id`。
- 集团与子公司证据不会被静默归并。

## 8. 报告智能体与研究工作台

### 8.1 建设目标

让报告成为持续研究入口，并把研究结论沉淀为 Claim、商机假设和行动对象。用户可以在不离开系统的情况下完成解释、补充研究、报告修订、业务验证、版本管理和正式导出。

### 8.2 工作台布局

桌面端可采用左右分栏，但必须遵循低认知负荷和渐进式披露：

- 左侧：当前业务视图、关键 Claim、商机假设、证据标记和版本切换。
- 右侧：智能体会话、操作状态、草案和下一步行动。
- 底部或抽屉：证据详情、原始搜索结果、审计记录。
- 首屏默认显示结论、置信度和行动，不直接铺满原始链接与审计细节。
- 外部证据、客户私有证据和内部知识使用稳定、可访问且不依赖特定品牌风格的视觉区分。
- 用户点击或展开引用后，再展示来源、抓取时间、可信度、快照和审计结果。

移动端允许报告和会话分 Tab 展示。

补充研究运行期间，右侧显示“规划—检索—抓取—提取—审计—生成草案”等可审计操作状态、当前步骤和异常信息。系统不得展示模型隐藏思维链、内部推理 Token 或未经整理的 Chain-of-Thought。

### 8.3 会话能力

#### FR-RPT-001 新建报告会话

- 一个报告可创建多个会话。
- 会话默认绑定当前已确认报告版本。
- 用户可命名会话，如“竞争对手分析”“技术方案讨论”。
- 会话记录不可因报告版本更新而丢失。

#### FR-RPT-002 选中内容提问

- 用户可选中报告中的段落、结论、表格行或证据引用发起问题。
- 系统将选区、所在章节、报告版本和关联证据加入上下文。
- 选区更新后，用户应能看到当前讨论对象。

#### FR-RPT-003 三类会话意图

系统将问题路由到三种模式：

1. **解释模式**：只使用现有研究资产，不调用外部搜索。
2. **补充研究模式**：创建子研究运行，允许搜索、抓取和新增证据。
3. **报告修订模式**：生成章节修改草案，不直接修改正式报告。

用户也可以手动指定模式。

#### FR-RPT-004 回答引用

- 所有关于目标客户的事实性回答必须引用外部公开证据或经过授权的客户私有证据。
- 所有关于我方产品能力的回答必须引用内部知识。
- 推断性回答必须标记“公开信息推断”或“销售判断”，不得伪装为客户确认。
- 无足够证据时明确回答“当前证据不足”。
- 引用可点击查看来源、摘要、抓取时间和可信度。

引用域统一使用：

```text
[external:证据ID]          客户公开事实
[customer-private:证据ID]  客户交流、RFP、会议纪要等授权材料
[internal:知识ID]          我方产品、方案、案例与能力
```

### 8.4 智能体澄清与人工确认

澄清机制用于处理会实质影响任务范围、证据选择、事实判断、产品匹配或报告质量的不确定性。它不是让智能体把所有微小选择都抛给用户，也不是展示模型隐藏思维链。

#### FR-CLR-001 澄清触发条件

执行前的计划检查和执行中的每个关键阶段都必须评估是否存在“重大不确定性”。以下情况必须发起澄清：

- 目标企业、集团/子公司或研究对象存在冲突，且不同选择会改变证据范围。
- 用户目标、报告用途、受众、研究范围、时间窗口、地区或业务线存在多种合理解释。
- 产品档案、产品范围、Skill 或研究模式的不同选择会显著改变结果。
- 关键证据互相冲突，无法仅依靠来源可信度和时效性规则得到稳定判断。
- 缺少形成关键 Claim、商机假设、价值判断或行动建议所需的用户私有事实。
- 下一步需要在启动前确认明显更高的预计费用、使用更高风险工具、切换数据域/模型路由或取得额外授权。
- 用户新指令与已确认范围、报告版本或安全策略冲突。

能够从已授权上下文、已确认配置或可靠证据中唯一确定的信息，不得重复询问用户。对不影响核心结论的次要缺口，系统可以继续，但必须把假设和影响写入运行记录。

#### FR-CLR-002 澄清问题格式

- 一次最多合并 3 个相互相关的问题，优先询问最能缩小研究空间的问题。
- 每个问题说明“需要确认什么”“为什么会影响结果”和“不回答会阻塞哪一步”。
- 存在有限选项时提供 2～3 个互斥选项；可以给出推荐项，但必须说明其影响。
- 始终允许用户自由输入，也允许用户选择“按推荐假设继续”或取消任务。
- 不得要求用户提供密码、API Key、访问令牌或超出任务必要范围的敏感信息。
- UI 只展示经整理的不确定点、选项和影响，不展示隐藏思维链或未经整理的内部推理。

#### FR-CLR-003 暂停、回答与恢复

```text
RUNNING
→ WAITING_FOR_INPUT(reason=CLARIFICATION)
→ QUEUED / CANCELLING
→ RUNNING / CANCELLED
```

- 创建澄清请求前必须提交当前 WorkUnit 允许保留的研究资产，并以同一事务写入请求、TaskEvent 和 `WAITING_FOR_INPUT` 状态；不得依赖 Redis Checkpoint。
- 等待期间不得创建新的搜索、抓取或模型调用工作单元；Worker 应释放执行资源，正在进行的不可中断调用按网络硬截止自然收敛。
- 澄清请求至少包含阶段、类别、重要性、问题、选项、推荐项、影响、`run_id`、`stage_run_id` 和 `control_version`。
- 用户回答、选择推荐假设或取消均必须先落库，再通过 `(task_id, clarification_id, response_id)` 幂等键恢复或终止运行。
- 网络重连、页面刷新或 Worker 重启后，待澄清问题仍然可见且只能恢复一次。
- 用户长时间未回答时保持暂停并允许提醒，不得超时后静默猜测并继续。
- 批量任务只暂停存在不确定性的行，其他有效行继续执行。
- 相同阶段、相同原因的重复问题应合并或标记为已替代，避免循环追问。

#### FR-CLR-004 回答使用与审计

- 用户回答作为显式用户上下文参与后续执行，并记录回答人、时间、原问题、选项和恢复运行。
- 如果用户授权按推荐假设继续，报告和相关 Claim 必须标明该假设及其影响，不能伪装为已验证事实。
- 用户只回答部分问题时，已回答部分可保存，但运行仍保持暂停，直到所有阻断项被处理或任务被取消。
- 正式报告生成前仍存在未处理的重大不确定性时，不得产出无警示的正式版本；可以输出明确标记缺口的草案或部分结果。
- 每次澄清的触发原因、等待时长、回答和恢复结果进入审计与质量评测。

### 8.5 研究资产持久化

#### FR-RPT-005 研究资产范围

任务执行和后续补充研究必须持久化：

- 研究问题与子问题。
- Planner 生成的搜索词。
- 搜索服务和返回序号。
- 原始搜索结果标题、URL、摘要和时间。
- 网页抓取状态和快照。
- 提取后的 Evidence。
- 评估结果和反思记录。
- Token、模型、耗时和失败原因。
- TaskRun、StageRun、WorkUnit、候选集、外部调用账本、TaskEvent、报告引用和审计状态。

断点续传以 PostgreSQL 中已完成工作单元、阶段游标和持久化资产为准；Redis 队列、缓存或历史 Checkpoint 均不得成为唯一恢复事实源。

#### FR-RPT-006 上下文构建

- 不允许每次把完整报告和全部原始材料直接塞入 LLM。
- ContextBuilder 根据问题选择相关报告章节、Claim、证据、搜索结果、客户私有材料和内部知识。
- 用户可展开查看“本次智能体使用了哪些上下文”。
- 上下文应记录对应报告版本，避免基于过期版本静默回答。

#### FR-CTX-001 有效上下文预算

模型标称上下文窗口不是产品可用预算。每次调用必须动态计算：

```text
有效输入预算 = min(
  模型上下文窗口 - 输出预留 - 系统/工具/Schema 预留 - 安全余量,
  Workspace 单次调用上限,
  Skill/智能体单次调用上限,
  当前 WorkUnit 单次输入硬上限
)
```

- 预算来自模型配置，不得硬编码假设所有 Provider 均支持 1M。
- 默认目标上下文包不超过有效输入预算的 65%；达到软阈值时执行选择或压缩，达到 80% 硬阈值时不得继续无控制追加。
- 阈值、输出预留和单次物理输入上限可配置；安全策略和数据域限制优先于窗口大小。累计 Token/费用预算只产生预估、告警和审计，不得在执行中静默截断上下文或降低强制质量门。
- 如果不可压缩的关键内容已超过硬阈值，系统必须拆分子任务或请求用户缩小范围，不得截断关键事实。

#### FR-CTX-002 四层上下文模型

| 层级 | 内容 | 处理规则 |
| --- | --- | --- |
| L0 固定上下文 | 系统与安全策略、目标企业、任务目标、当前报告版本、用户已确认范围、澄清回答、授权、当前问题 | 原文保留，不做生成式压缩；仅允许结构化去重 |
| L1 工作上下文 | 当前阶段状态、最近相关消息、当前计划、活跃 Claim、支持与反向证据、待办和错误 | 按相关性、时效性、权威性和任务阶段动态选择 |
| L2 压缩上下文 | 较早会话、已完成研究步骤和大段材料的结构化摘要 | 必须保留来源资产 ID、事实/假设/反证/未决问题分类和压缩版本 |
| L3 原始档案 | 全量消息、原始文档、搜索结果、Evidence、工具结果、StageRun 资产和 TaskEvent | 不因压缩删除；按权限检索回填，不默认整包发送给模型 |

L0 中至少包括：用户澄清回答、客户确认事实、主体消歧结果、数据授权、数字及单位、日期和时间范围、硬性限制、当前 Claim 状态、明确反证以及未解决冲突。这些内容不得被摘要改写为含义不确定的自然语言。

#### FR-CTX-003 结构化压缩与来源追踪

- 压缩输出使用结构化 `ContextSnapshot`，分别记录已确认事实、推断、假设、反证、冲突、决策、未决问题、已完成步骤和下一步。
- 每个压缩条目必须关联原始消息、Evidence、Claim、文档页码、工具结果或运行事件 ID；引用覆盖率必须为 100%。
- `external`、`customer_private`、`internal` 三个数据域分别压缩和存储，不得在摘要阶段混成无法区分来源的一段文本。
- 客户私有或内部材料只能使用该数据域获批的模型进行压缩；没有可用模型时采用抽取式压缩或保持原文检索，不得回退公共云。
- 压缩快照记录模型、Prompt/规则版本、输入资产清单、Token、生成时间、报告版本和内容哈希。
- 禁止无限“摘要再摘要”。重新压缩时应从原始资产和最近有效快照重建，并限制压缩代际，避免事实漂移。

#### FR-CTX-004 触发与回填

以下情况触发上下文重新选择或生成快照：

- 预计输入达到软阈值。
- 会话、研究阶段或报告版本发生切换。
- 完成一次补充研究、用户澄清或报告草案确认。
- Claim 被确认、否定、标记冲突或过期。
- 模型路由发生变化，目标模型上下文窗口更小。

当用户追问压缩摘要中未包含的细节、引用或反证时，ContextBuilder 必须从 L3 原始档案重新检索并回填 L1，而不是仅依据摘要回答。用户可查看本次上下文清单、哪些内容来自压缩快照以及对应原始来源。

#### FR-CTX-005 压缩质量门

- 关键事实、数字、单位、主体、时间、授权、用户澄清回答和反证丢失率必须为 0%。
- 压缩后回答仍必须满足引用覆盖、引用正确性、三域隔离和 Claim 一致性要求。
- 压缩前后使用同一黄金问题集进行盲评；若事实正确性、反证召回或行动建议质量显著下降，应降低压缩率或回退到原始资产重建，而不是继续沿用低质量快照。
- 所有压缩与回填操作进入审计日志；压缩失败不删除或覆盖原始资产。

### 8.6 客户私有证据与 Claim Registry

#### FR-PRV-001 客户私有证据域

客户访谈记录、会议纪要、客户邮件、RFP、需求文档、CRM 备注、现场调研和合作伙伴反馈归入 `customer-private` 证据域。

- 上传或录入时必须记录来源、授权范围、敏感级别、可见范围、采集时间和录入人。
- 客户私有内容不得发送给 Search Provider，也不得进入未获批准的云端模型。
- 系统抽取出的内容默认是 Claim 草案；只有用户确认或明确标记“客户已确认”后，才可提升真实性状态。
- “来自客户材料”不等于“客户已确认”，RFP 模板、转述和历史材料仍需区分。

#### FR-CLM-001 Claim Registry

每个可被报告、问答、产品匹配或商机假设引用的关键结论建立独立 Claim，至少包含：

- 结论内容、结论类型和适用主体。
- 支持证据与反向证据。
- 真实性状态：未验证、公开证据支持、销售判断、客户确认、存在冲突、已否定。
- 置信度、首次发现时间、最近验证时间和失效时间。
- 生成来源、确认人及变更历史。

同一事实在报告、会话和商机卡中必须引用同一 Claim，不得各自重新生成互不关联的判断。Claim 过期或被否定后，所有依赖对象必须显示影响提示并重新计算相关结论。

### 8.7 多种业务视图与下一步行动

同一套研究资产至少支持以下视图，不要求销售必须阅读完整长报告：

1. 30 秒客户摘要。
2. 一页式 Account Brief。
3. 商机假设卡。
4. 售前深度报告。
5. 高管简报。
6. 首次沟通或需求访谈提纲。
7. 方案匹配与能力缺口表。
8. 竞争作战卡。
9. 下一步行动清单。

v3.2 首期交付 30 秒摘要、一页式简报、商机假设卡、深度报告和下一步行动；其余视图在 v3.4 随业务对象补齐。

#### FR-ACT-001 NextBestAction

下一步行动不是报告文本段落，而是结构化对象，至少记录：行动目标、目标角色、建议渠道、沟通角度、使用证据、建议问题、配套材料、前置条件、期望结果、负责人、计划日期、状态和完成结果。

- 智能体可以生成邮件、会议议程、访谈提纲和破冰话术草案，但不得自动发送。
- 行动完成后必须记录结果，并允许触发 Claim、商机假设或资格卡更新。
- 缺少负责人或计划日期的行动只能保存为建议，不能进入“待执行”状态。

### 8.8 补充研究

#### FR-RPT-007 创建子研究运行

- 用户问题需要新事实时创建 `follow_up_research_run`。
- 子研究继承目标企业、能力档案、产品、Skill、费用告警阈值、上下文物理上限和安全策略，并创建独立耐久 Run。
- 用户可在开始前查看研究计划和成本估算。
- 子研究结果独立记录，可选择是否并入报告。

#### FR-RPT-008 补充证据审计

- 新证据必须经过来源可信度、相关性、时效性和 Claim Audit。
- 新旧证据冲突时不得只保留新证据。
- 智能体应解释冲突并降低结论置信度。

### 8.9 报告修改与版本

#### FR-RPT-009 生成修改草案

- 用户可对章节或整个报告发起修改。
- 草案必须记录修改原因、使用证据和生成它的会话消息。
- 草案与正式报告分离。

#### FR-RPT-010 差异确认

- UI 提供章节级和文本级 Diff。
- 用户可全部接受、部分接受或拒绝。
- 部分接受时生成新的组合草案供再次确认。

#### FR-RPT-011 版本不可变

- 已确认报告版本不可原地修改。
- 每次接受草案生成新版本。
- 新版本记录父版本、修改人、修改时间、会话、研究运行和新增/删除证据。
- 旧版本始终可查看和导出。

#### FR-RPT-012 导出

- 默认导出最新已确认版本。
- 用户可以选择历史版本。
- 未确认草案不能以“正式报告”名义导出；可以导出为带水印的“草案”。

### 8.10 并发与冲突

- 多个会话可同时基于同一版本产生草案。
- 当草案所基于的报告版本已过期时，接受前必须重新基于最新版计算 Diff。
- 系统不得自动合并相互冲突的草案。

### 8.11 验收标准

- 用户可围绕报告连续进行至少 20 轮对话并保留上下文。
- 智能体在执行前和执行中能够识别重大不确定性、暂停任务并请求澄清；用户回答后从 PostgreSQL 中下一未完成 WorkUnit 幂等恢复。
- 待澄清期间不继续调用搜索、抓取或付费模型；用户未回答时不得静默猜测。
- 澄清问题包含原因、影响和可选回答；批量任务只暂停受影响的行。
- 在长会话、长报告和多轮研究样本中，系统按目标模型、Workspace、Skill 和当前 WorkUnit 单次物理输入上限计算有效上下文，不依赖固定窗口值；累计费用只告警，不改变强制质量输入。
- L0 固定上下文、关键事实、数字单位、澄清回答、反证、授权和未决冲突在压缩后保持原义，关键内容丢失率为 0%。
- 每个 ContextSnapshot 条目可以追溯到原始资产；三证据域分离，用户追问细节时可从原始档案回填。
- 压缩前后黄金问题盲评不出现显著质量下降，压缩失败不会覆盖或删除原始资产。
- 解释模式不会触发外部搜索。
- 补充研究结果可追溯到搜索词、搜索结果和新证据。
- 事实性回答引用覆盖率达到 100%。
- 引用正确性可通过人工或自动评测验证，而不只检查是否存在引用标记。
- 外部、客户私有和内部三个证据域不会混用。
- 同一 Claim 的状态变化会同步影响报告、问答和商机假设。
- 用户可不打开完整报告，直接获得一页简报、商机假设卡和下一步行动。
- 接受草案后形成新版本，原版本内容和导出结果不变。
- 版本冲突会被发现并要求重新确认。

## 9. Skill V2 专家体系

### 9.1 建设目标

把 Skill 从“维度和关键词配置”升级为能真正控制研究目标、问题树、工具使用、信源、评估、停止条件和报告结构的专家工作流。

### 9.2 分阶段交付与用户权限

Skill 标准化仍是已确认方向，但不在 v3.3 一次性建设完整平台。

| 用户 | v3.3 核心能力 | v3.5 增强能力 |
| --- | --- | --- |
| 销售人员 | 选择已发布的场景模板，不直接编辑 Skill 文件 | 查看适用说明和版本变化 |
| 售前/行业专家 | 修改研究问题、信源、判断标准、报告结构和子 Skill 选择 | 高级触发评测和版本对比 |
| Skill 管理员 | 编辑标准目录、编译、测试、发布和归档 | 可视化 DAG、GitHub/离线导入和上游更新 |

v3.3 试点只要求交付一个明确行业场景的一级 Skill 和 3～5 个可复用二级 Skill，以验证专家策略是否真实改善研究质量。目录标准、两层模型、编译执行、小白 UI 和基础评测属于 v3.3 核心；GitHub 直连、高级编排图和上游同步属于 v3.5。

### 9.3 Skill 标准目录

本项目 Skill 使用以下标准目录：

```text
skill-name/
├── SKILL.md                         # 必需：元数据、触发范围、核心工作流和引用导航
├── references/                      # 可选：专业知识和结构化规则
│   ├── research-playbook.md
│   ├── evidence-rubric.md
│   ├── report-outline.md
│   └── orchestration.yaml
├── assets/                          # 可选：模板、图标、示例资产
├── tests/                           # 本项目扩展：黄金用例和评测数据
│   └── cases.yaml
└── agents/
    └── openai.yaml                  # 可选：显示信息和依赖声明
```

所有版本均不支持执行外部 `scripts/` 代码。导入包中的脚本只可保留在隔离区用于审查，不会进入可发布版本。

### 9.4 SKILL.md 基本约束

#### FR-SKL-001 元数据

`SKILL.md` 必须包含 YAML Frontmatter：

```yaml
---
name: public-sector-customer-service-research
description: 研究政务或公共服务机构的智能客服与联络中心商机。用于识别客服系统现状、招投标、政策驱动、用户痛点和竞争锁定；不用于纯技术代码审查。
---
```

约束：

- `name` 使用小写字母、数字和连字符。
- `description` 同时说明“做什么、何时使用、何时不使用”。
- Skill 主体保持精炼，复杂内容放入直接引用的 `references/` 文件。
- 引用深度不超过一层。
- 每个 Skill 聚焦一个明确职责。

### 9.5 两层 Skill

#### FR-SKL-002 一级场景 Skill

一级 Skill 负责：

- 解释业务场景和适用边界。
- 定义研究目标和问题树。
- 选择并编排二级 Skill。
- 定义执行顺序、并行关系和条件分支。
- 定义整体停止条件、预算和报告结构。
- 聚合不同子 Skill 的证据和结论。

示例：`public-sector-customer-service-opportunity`。

#### FR-SKL-003 二级原子 Skill

二级 Skill 负责单一专业能力，例如：

- `resolving-target-company`
- `researching-bidding-history`
- `analyzing-policy-drivers`
- `mining-customer-pain-points`
- `detecting-vendor-lock-in`
- `matching-product-capabilities`

二级 Skill 可以被多个一级 Skill 复用。

#### FR-SKL-004 编排定义

- 父子关系写入 `references/orchestration.yaml`。
- 引用子 Skill 使用稳定 `name` 和版本约束。
- 系统必须检测循环依赖。
- 父 Skill 禁用、缺少子 Skill 或版本不满足时不得发布。

### 9.6 Skill 单一事实来源

#### FR-SKL-005 文件与数据库关系

- 标准 Skill 目录是正式来源。
- 数据库保存元数据索引、启停状态、发布状态、来源、版本哈希和编译结果。
- UI 修改必须写回 Skill 文件并重新编译。
- 禁止 UI 只修改数据库 `config_yaml` 而不更新 Skill 文件。

### 9.7 Skill 编译器

#### FR-SKL-006 编译输出

`SkillCompiler` 将 Skill 目录编译为执行器可消费的结构，包括：

- 触发条件和适用边界。
- DimensionGoal 和研究问题树。
- 搜索关键词模板。
- 信源优先级、禁止信源和必需信源。
- 噪音过滤规则。
- 必须提取字段。
- 证据数量、来源多样性和时效性要求。
- 评分权重和质量阈值。
- 子 Skill DAG。
- 报告章节和输出 Schema。
- 外部 Agent 任务。
- 预算和停止条件。

编译完成后必须生成可视化 Dry Run 计划，至少展示：

- 预计触发的一级和二级 Skill。
- 将调用的内置工具及调用顺序。
- 每个步骤允许访问的证据域。
- 可能发送给模型的数据类型和获批模型路由。
- 预计搜索次数、Token、成本和停止条件。
- 使用 Mock 数据得到的结构化输出与安全告警。

Dry Run 只执行编译、静态分析和受控 Mock，不访问真实客户数据、不发起外部写操作，也不执行导入包中的任意代码。所谓“隔离沙盘”仅指解析和模拟边界，不构成外部代码执行授权。

#### FR-SKL-007 执行消费

- Planner 必须消费 Skill 的问题树和关键词策略。
- Researcher 必须消费信源策略和工具限制。
- Extractor 必须消费字段要求和证据 Schema。
- Evaluator 必须消费评估标准和阈值。
- ReportComposer 必须消费报告结构。
- 不允许继续仅通过 `dimensions` 决定 Skill 行为。

### 9.8 面向小白的 UI

#### FR-SKL-008 向导模式

向导至少包含：

1. Skill 名称与用途。
2. 适用行业和触发场景。
3. 不适用场景。
4. 希望回答的核心问题。
5. 研究步骤。
6. 推荐搜索方向。
7. 信源偏好与禁止来源。
8. 成功标准和证据要求。
9. 报告章节。
10. 子 Skill 选择和顺序。
11. 测试用例。

保存时生成标准 `SKILL.md` 和引用文件。

#### FR-SKL-009 专家模式

- Markdown 编辑器。
- 目录树和资源文件管理。
- 基础子 Skill 列表和顺序编辑；完整可视化编排图在 v3.5 交付。
- 编译预览。
- 版本 Diff。
- 触发测试。
- 黄金用例执行结果。

向导模式与专家模式编辑的是同一套 Skill 文件。

### 9.9 GitHub 导入（v3.5 增强项）

#### FR-SKL-010 导入输入

用户提供：

- GitHub 仓库 URL。
- 分支、Tag 或 Commit；最终必须解析为 Commit SHA。
- Skill 所在目录。

#### FR-SKL-011 导入检查

导入前检查：

- 是否存在 `SKILL.md`。
- Frontmatter 是否有效。
- 文件数量、单文件大小和总大小。
- 路径穿越、软链接逃逸、压缩炸弹。
- 可执行代码和二进制文件。
- 外部网络、MCP、工具和依赖声明。
- Prompt Injection 和高风险指令。
- 许可证、作者和来源。
- 与现有 Skill 的名称和版本冲突。

#### FR-SKL-012 一次性转换

- Codex/Claude 风格 Skill 在导入阶段转换成本项目标准。
- 原始目录保存为只读来源快照。
- 转换后展示缺失项、推断项、被移除项和风险项。
- 用户确认后生成新的本地 Skill 版本。
- 运行时不读取原始格式，不维护多套解析分支。

#### FR-SKL-013 更新上游

- 系统可检查原仓库是否有新 Commit。
- 更新必须重新执行检查、转换、Diff、试运行和确认。
- 不自动覆盖本地已修改版本。

### 9.10 生命周期与评测

#### FR-SKL-014 生命周期

状态包括：

```text
DRAFT → VALIDATING → TESTING → PUBLISHED → DEPRECATED → ARCHIVED
```

- 只有 `PUBLISHED` Skill 可用于正式任务。
- 已被任务引用的版本不可删除，只能归档。
- 新版本发布不影响历史任务的复现。

#### FR-SKL-015 黄金测试集

每个正式 Skill 至少包含：

- 3 个应触发案例。
- 3 个不应触发案例。
- 3 个真实研究用例。
- 最低证据数量和来源类型要求。
- 报告章节完整度要求。
- 禁止出现的高风险行为。

#### FR-SKL-016 评测指标

- 触发准确率。
- 问题树覆盖率。
- 搜索词多样性。
- 权威信源占比。
- 证据有效率。
- Claim 引用覆盖率。
- 幻觉和错误引用率。
- 报告章节完整度。
- Token、耗时和成本。
- 人工采纳率。

### 9.11 验收标准

- 标准 Skill 可被 Codex/Claude 风格工具识别其 `name` 和 `description`。
- UI 创建 Skill 后能生成完整标准目录。
- 同一个 Skill 在 UI 和文件模式下内容一致。
- 一级 Skill 可组合至少 3 个二级 Skill 并正确执行。
- 循环依赖会在发布前阻断。
- Skill 的关键词、信源、评估标准和报告结构均实际影响执行结果。
- v3.3 试点 Skill 相比当前简单 Skill，在人工专家盲评中达到预先约定的质量提升门槛。
- Dry Run 能展示工具、数据域、模型路由、预算和安全风险，且不访问真实客户数据。
- v3.5 验收时，GitHub 导入不会执行外部代码，导入结果可完成检查、转换、Diff、Mock 试运行和人工确认。

## 10. 批量模板与导入升级

### 10.1 建设目标

让普通用户通过下载标准模板快速准备准确数据，并支持标准调研和只填写企业名称的批量商机线索发现。

### 10.2 模板中心

#### FR-BAT-001 模板列表

模板中心展示：

- 模板名称。
- 适用模式和 Skill。
- 模板版本。
- 必填字段和可选字段。
- 示例截图。
- 最近更新时间。
- XLSX 和 CSV 下载。

#### FR-BAT-002 模板类型

首批模板：

1. 标准客户调研模板。
2. 招投标调研模板。
3. 政策驱动调研模板。
4. 商机线索发现模板。
5. 高级自定义模板。

### 10.3 XLSX 结构

推荐包含：

| 工作表 | 内容 |
| --- | --- |
| 批量任务 | 用户填写数据 |
| 字段说明 | 字段含义、格式、是否必填、示例 |
| 示例数据 | 正确示例和常见错误示例 |
| 模板元数据 | 模板 ID、版本、模式；默认隐藏 |

XLSX 应对 Skill、Profile、Depth、地区等字段提供下拉校验。

### 10.4 字段规则

#### 标准模式

- 企业名称：必填。
- 需求方向：必填。
- 企业官网、信用代码、行业、地区、业务目标、时间范围、已知线索：可选。
- Skill、Profile、Depth：可由批次统一设置，也可逐行覆盖。

#### 线索发现模式

- 企业名称：必填。
- 企业能力档案：可在批次层统一选择，逐行可选覆盖。
- 产品：可选；为空时由系统自动选择。
- 需求方向：可选；为空时由系统根据产品和目标企业生成待验证的商机假设。
- 所有企业消歧字段均可选。

### 10.5 导入流程

#### FR-BAT-003 上传与预览

- 支持 `.xlsx` 和 `.csv`。
- 默认推荐 XLSX。
- 显示文件名、模板版本、总行数、有效行和警告。

#### FR-BAT-004 字段映射

- 自动映射标准列名和常见别名。
- 用户可以手动更改映射。
- 未识别列可忽略或映射到备注。
- 必须防止同一个原始列映射到多个标准字段。

#### FR-BAT-005 逐行验证

验证：

- 企业名称为空或过短。
- 企业重复。
- URL、信用代码和股票代码格式。
- Skill、Profile、Depth 枚举。
- 模板版本。
- 能力档案和产品是否存在。
- 逐行覆盖与批次设置是否冲突。

#### FR-BAT-006 Dry Run

- 用户可选择 1～5 条代表样本。
- 系统展示研究计划、预计时间、Token 和费用。
- 线索发现模式 Dry Run 必须展示候选产品、假设依据和选择理由。
- Dry Run 不创建正式批次。

#### FR-BAT-007 创建与错误隔离

- 只有通过验证或用户明确接受警告的行进入执行。
- 错误行可下载为修正文件。
- 单行失败不阻塞整个批次。
- 批次详情显示消歧、产品匹配、研究、报告等阶段进度。

### 10.6 模板版本

- 服务端维护当前模板版本。
- 旧模板上传时提示升级，不做永久运行时兼容。
- 用户可一键转换为当前模板并下载转换结果。
- 转换属于一次性数据迁移，后续只按当前模板执行。

### 10.7 验收标准

- 普通用户下载模板后无需阅读额外文档即可完成填写。
- 1000 行文件可正常预览、验证和创建批次。
- 行业、地区、能力档案、产品、Skill、Profile、Depth 能完整传递到 Worker。
- 线索发现模式仅填写企业名称也可进入消歧和研究流程。
- 错误行不会阻塞有效行。

## 11. 企业能力中心

### 11.1 建设目标

让用户把企业产品、解决方案、案例、资质和能力边界沉淀为可维护、可引用、可匹配的内部知识，使系统能够根据目标客户信号自动推荐我方产品和切入策略。

### 11.2 档案层级

```text
默认 Workspace
└── 企业能力档案（多个）
    ├── 企业与品牌信息
    ├── 产品线（多个）
    │   └── 产品（多个）
    ├── 解决方案（多个）
    ├── 客户案例（多个）
    ├── 资质与认证（多个）
    ├── 差异化能力
    ├── 交付、价格与区域边界
    ├── 不适用场景
    └── 内部知识文档（多个）
```

### 11.3 能力档案

#### FR-CAP-001 多档案

- Workspace 可创建多个能力档案。
- 每个档案可设置名称、所属企业、品牌、默认行业和地区。
- 可设置一个默认档案。
- v3.3 试点可以只启用一个默认档案，但数据模型和 UI 必须支持用户已确认的多档案、多产品结构。
- 单任务选择一个主档案；v3.4 首期不支持单任务同时组合多个主档案。

#### FR-CAP-002 档案状态

状态：草稿、可用、停用、归档。

- 只有可用档案可用于正式任务。
- 已被历史报告引用的档案版本不可物理删除。

### 11.4 产品与方案

#### FR-CAP-003 产品字段

产品至少包含：

- 名称、产品线、版本。
- 一句话价值主张。
- 解决的问题。
- 核心能力。
- 目标行业和客户规模。
- 典型使用场景。
- 交付方式和集成要求。
- 资质要求。
- 价格范围或商务边界。
- 区域和服务限制。
- 竞争优势。
- 相对常见竞品、客户自研或维持现状的差异化说明。
- 已知短板。
- 不适用场景。
- 关联案例和资料。

#### FR-CAP-004 解决方案

- 解决方案可组合多个产品。
- 解决方案定义行业、场景、客户痛点、交付路径和预期收益。
- 产品与解决方案均支持版本。

#### FR-CAP-005 案例与资质

- 案例记录客户行业、客户规模、问题、方案、结果和可公开范围。
- 资质记录名称、颁发机构、有效期、适用产品和适用行业。
- 过期资质不得被自动用于“Why Us”。

### 11.5 文档上传与处理

#### FR-CAP-006 支持格式

首期支持：

- PDF。
- DOCX。
- PPTX。
- XLSX。
- Markdown/TXT。
- 网页 URL。

图片型或扫描 PDF 进入 OCR 队列。密码保护文件明确报错，不尝试绕过密码。

#### FR-CAP-007 文档处理流程

```text
上传
→ 病毒/类型/大小检查
→ 文本与结构解析
→ 标题、页码和表格切分
→ 能力实体抽取
→ 用户校对
→ 发布到能力档案
```

#### FR-CAP-008 结构化抽取

从文档中识别：

- 产品和版本。
- 功能与能力。
- 目标行业和场景。
- 客户痛点。
- 技术与部署要求。
- 案例和量化结果。
- 资质。
- 价格、区域和交付限制。
- 免责声明和不适用场景。

抽取结果必须经过用户确认，不能直接成为正式能力卡。

#### FR-CAP-009 重复与版本

- 根据文件哈希检测重复上传。
- 同一资料的新版本保留历史版本。
- 产品更新后，历史报告仍引用当时使用的产品版本。

### 11.6 检索与引用

#### FR-CAP-010 混合检索

- 结构化产品卡作为主要匹配依据。
- RetrievalRouter 先判断问题意图：产品参数、资质、区域和版本等问题优先使用结构化精确匹配与过滤；行业痛点、方案和案例类问题使用全文与向量混合检索。
- 关系检索可先使用结构化关联表实现；只有试点评测证明必要时才引入专门图数据库。
- 返回内容必须保留文档、章节、页码或工作表位置。

#### FR-CAP-011 内部知识引用

报告和对话中的我方能力结论引用格式与外部证据明显区分：

```text
[external:证据ID]  目标客户外部事实
[internal:知识ID]  我方产品与能力
```

- 内部知识不能作为客户需求事实的证明。
- 外部证据不能证明我方具备某项能力。

### 11.7 权限与保密

- 用户只能访问其所在 Workspace 授权范围内的能力档案。
- 内部文档不得发送到搜索 Provider。
- 发送给 LLM 的内部内容必须遵循最小必要原则。
- 每次内部知识检索和 LLM 使用记录审计日志。
- 删除档案时提供“停止使用”和“彻底删除”两种模式；彻底删除受历史引用和保留策略约束。

### 11.8 验收标准

- 一个 Workspace 可创建至少 10 个能力档案。
- 所有能力档案归属于 Workspace，而不是只绑定某个个人用户。
- 每个档案可维护多个产品线和产品。
- 文档抽取结果可由用户校正后发布。
- 产品限制和不适用场景能进入匹配判断。
- 内部资料不会出现在外部搜索请求中。
- 报告能区分外部证据、客户私有证据和内部知识引用。

## 12. 商机线索、假设与售前作战

### 12.1 建设目标

用户只需选择企业能力档案并输入目标企业名称，系统即可发现需求信号、选择候选产品和研究策略，并生成待销售验证的商机假设。系统不得把公开信号直接创建为正式商机。

### 12.2 业务阶段与定义

```text
目标客户 Account
→ 客户事件或需求信号 Signal
→ 商机假设 OpportunityHypothesis
→ 销售接受 SalesAccepted
→ 客户侧验证 CustomerValidated
→ 正式商机 Opportunity
→ 方案塑造 SolutionShaping
→ 投标或采购 Proposal/Tender
→ 成交或丢单 Won/Lost
```

- **Signal**：招标、政策、组织变化、投诉、技术建设等被证据支持的客观事件。
- **OpportunityHypothesis**：基于 Signal、Claim 与我方能力提出的可验证业务假设。
- **SalesAccepted**：销售认为值得投入验证，不代表客户需求已确认。
- **CustomerValidated**：通过客户交流或客户私有材料确认问题、价值或采购窗口。
- **Opportunity**：达到 Workspace 配置的阶段门后，由用户确认创建的正式销售机会。

系统界面和导出不得在 CustomerValidated 前把假设称为“客户已确认商机”。

### 12.3 输入

#### 必填

- 目标企业名称。

#### 条件必填

- 企业能力档案：如果 Workspace 只有一个可用默认档案则自动选中，否则用户选择。

#### 可选

- 目标企业官网、信用代码、地区、行业等消歧信息。
- 指定产品或产品线。
- 时间范围。
- 业务目标。
- 已知线索。
- 报告 Profile 和 Depth。

### 12.4 自动流程

```text
目标企业消歧
→ 读取能力档案和产品组合
→ 发现并登记需求信号与 Claim
→ SkillRouter 选择一级 Skill
→ 展开二级专家 Skill
→ 执行外部研究
→ Evidence 标准化、审计和时间归一化
→ 采购/合同/政策生命周期与客户能力基线
→ 能力缺口、触发因素与介入窗口分析
→ OpportunitySkeptic 反证优先审查
→ Opportunity Intelligence Gate 生成 G0～G5/GX 裁决
→ 初步筛选 1～3 个候选产品并执行 ProductFitGate
→ 裁决后评分
→ 生成商机假设卡和下一步验证行动
→ 销售接受、拒绝或暂缓
```

### 12.5 Opportunity Intelligence Gate（阻断级）

OIG 位于证据审计之后、商机评分和报告生成之前，完整规则见 `docs/OPPORTUNITY_INTELLIGENCE_GATE_SPECIAL_PLAN.md`。

六层裁决顺序为：

```text
Time → Capability → Gap → Trigger → Window → Fit
```

机器裁决等级与人工销售阶段分离：

| 等级 | 含义 | 上限 |
| --- | --- | --- |
| G0 | 无关或不可用信息 | 不创建 Signal |
| G1 | 历史能力证据 | 进入能力基线，不作为当前正向商机 |
| G2 | 待验证缺口假设 | 不生成确定性销售行动 |
| G3 | 当前需求信号 | 创建 Signal 和补证动作 |
| G4 | 潜在介入窗口 | 可生成待销售判断的商机假设 |
| G5 | 可介入商机候选 | 机器硬门槛通过，仍需 SalesAccepted/CustomerValidated |
| GX | 暂无明确商机或不建议推进 | 合法终态，记录反证和重验条件 |

原专项 O6/O7 不另建机器状态，分别使用现有 `CustomerValidated` 和 `Opportunity`。GateDecision 是指定 `analysis_as_of_date` 下的不可变机器裁决快照，不得自动提升人工销售阶段。

### 12.6 功能需求

#### FR-OPP-001 Signal 与商机假设

- 系统先把招标、政策、组织变化、客户反馈等客观事件登记为 Signal，并绑定来源 Claim。
- 系统根据 Signal、产品解决的问题、适用行业和目标企业画像生成候选商机假设。
- OIG Gate 因子必须先按唯一来源关系物化为 Claim；同一 Gate 因子重试不得重复创建 Claim，假设只能引用这些可审计 Claim，不得复制一份无来源结论。
- 假设只是待验证方向，不得作为客户已确认需求或正式商机。
- 每个假设至少记录：客户问题假设、业务影响假设、触发事件、候选产品、客户证据、反向证据、硬性阻断项、当前阶段、下一验证动作、负责人、有效期、生成原因和置信度。
- 商机假设状态至少包括：草稿、待销售判断、销售接受、销售拒绝、待客户验证、客户已验证、已转正式商机、已过期。
- 假设过期后不得继续参与经营漏斗，除非重新验证。

#### FR-OPP-002 产品筛选与评分

产品匹配采用“硬门槛 + 加权评分 + 置信度校准”，不再使用各维度直接相乘。

第一步，检查硬门槛：

- 禁止行业或客户类型。
- 缺少必要资质。
- 无法在目标区域交付。
- 超出产品能力边界。
- 明确的安全、合规或商务阻断。

命中硬性阻断时输出“不建议推进”或“需合作伙伴补齐”，不得仅通过其他维度高分抵消。

第二步，计算可配置的加权评分：

```text
综合评分 =
需求强度 × 需求权重
+ 产品适配度 × 产品权重
+ 时机成熟度 × 时机权重
+ 竞争可胜度 × 竞争权重
+ 商务可行性 × 商务权重
```

- 权重按行业、产品和资格框架配置并记录版本。
- 同时展示推荐分、证据置信度、信息完整度、缺失字段和影响最大的正负因素。
- 没有足够匹配产品时允许输出“暂不建议推进”。

#### FR-OPP-003 研究计划预览

标准和深度模式在执行前展示：

- 目标企业识别结果。
- 候选产品。
- 商机假设。
- 推荐 Skill。
- 研究维度。
- 成本和耗时估算。

快速模式可以允许用户选择直接执行。

#### FR-OPP-004 商机假设输出

线索发现模式至少输出：

- 目标企业确认信息。
- 客户现状与关键事件。
- 客户需求信号。
- 对应产品和解决方案。
- 匹配理由和证据。
- 不匹配项与能力缺口。
- 商机假设及所处阶段。
- 竞争锁定风险和可能的非供应商替代方案。
- 决策角色推断及真实性状态。
- 结构化下一步验证行动。
- 置信度和研究局限。

#### FR-OPP-005 利益相关者地图（v3.4）

StakeholderMap 至少覆盖经济决策、业务、技术、安全合规、采购、使用部门、内部支持者和反对者等角色，并记录：姓名或角色、部门、影响力、态度、目标、顾虑、我方关系强度、信息来源、真实性状态和建议沟通策略。

- 真实性状态必须区分公开信息推断、销售判断和客户确认。
- 缺少可靠信息时允许只记录角色类型，不强行生成姓名。
- 智能体只能生成候选和建议，用户负责确认或修正。

#### FR-OPP-006 商机资格卡与阶段门（v3.4）

- 系统提供可配置资格框架，可参考 MEDDPICC、BANT、SPICED 等方法，但不绑定单一销售方法。
- 至少评估痛点重要性、量化影响、预算可能性、时间窗口、关键角色、决策标准、采购流程、内部支持者、竞争态势、交付与商务可行性。
- Workspace 可以配置从信号、问题验证、价值验证、预算/窗口验证到正式商机的阶段门。
- 未通过阶段门时不得提升为正式商机。用户只能补充或修正资格事实；阶段门配置变更必须进入审计且只影响后续判断。

#### FR-OPP-007 竞争者与竞争作战卡（v3.4）

竞争对象不仅包括商业竞品，还包括现有供应商、客户自研、继续使用现有系统、延期建设和暂不投资。

CompetitiveBattlecard 至少记录：

- 竞争对象类型、名称及来源。
- 现有合同、可能到期时间和切换成本。
- 对手优势、弱点和我方差异化。
- 客户决策标准和必须赢下的关键指标。
- 我方风险、禁止承诺项和竞争性发现问题。
- 可联合的生态伙伴。

未经证据支持的竞品存在、合同和到期时间必须标记为推断，不得写成事实。

#### FR-OPP-008 价值假设（v3.4）

价值假设可记录当前成本、效率提升、风险降低、收入或体验影响、预计投入、实施周期、ROI、回收周期、关键假设、敏感性分析和待客户验证参数。

- AI 只能生成计算模型、行业基准候选和待填参数，不能编造客户收入、成本、预算或 ROI。
- 每个数值必须标明来源、币种、时间范围和“客户提供/行业基准/用户假设”状态。
- 缺少关键参数时只展示计算框架，不输出伪精确结果。

#### FR-OPP-009 最小业务输出契约（v3.4）

- 支持将客户、商机假设、Claim、资格状态、下一步行动和正式商机导出为 CSV/JSON。
- 提供版本化 Webhook 契约供 CRM/OA 后续集成。
- 首期不自动向外部系统推送；每次导出或调用由用户确认并记录审计。
- 系统不承担完整 CRM 的联系人、报价、合同和回款管理。

#### FR-OPP-010 防止强行匹配

- 系统不得为了输出商机而强行推荐产品。
- 证据不足、时机不成熟、交付条件不满足时应降级或否定推荐。
- “暂无明确商机”是合法结果。

#### FR-OIG-001 分析截止日期与时间归一化

- 每个 ResearchRun 冻结 `analysis_as_of_date` 和 Workspace 时区，历史报告按原日期回放。
- Evidence 支持发布日期、事件日期、截止日期、政策生效/失效、合同开始/结束、日期精度和推断来源。
- 时间未知的核心证据可以进入背景或补证，但不能直接证明当前窗口。
- 已截止招标且无延期证据时，禁止描述为开放采购。
- 推断合同到期只输出时间范围、置信度和依据，不得伪装为确定日期。

#### FR-OIG-002 采购性质与生命周期

- 采购性质至少区分一次性建设、许可、订阅、运维、运营、框架、人力、咨询、安全和混合项目。
- 采购生命周期至少包括 PLANNED、SOURCING、TENDERING、EVALUATING、AWARDED、CONTRACTED、IMPLEMENTING、LIVE、MAINTAINING、EXPANDING、REPLACING、CANCELLED、EXPIRED 和 UNKNOWN。
- 中标、签约、建设、验收、投产和维保改变原采购项目状态；扩容、替换和重招创建新的事件或假设。
- 只有历史招标且无结果时进入 UNKNOWN/EXPIRED 和补证任务，不得判断为当前明确商机。

#### FR-OIG-003 合同生命周期与窗口

- 合同记录研究所需的最小字段：项目、采购方、供应商、起止时间、服务期、续约/延期选项、服务范围、来源、推断字段和置信度。
- 合同状态至少包括 ACTIVE、RENEWAL_OBSERVATION、RENEWAL_WINDOW、EXPIRED、EXTENDED、RE_TENDERED、RENEWED、REPLACED 和 TERMINATED。
- 12/6/3 个月仅作为可配置初始窗口；不同产品、行业和采购性质可以覆盖。
- 自动续约、延期条款和长期有效合同降低近期重招概率；到期窗口只生成观察或验证动作，不能自动证明新采购。

#### FR-OIG-004 客户能力基线与缺口

- 客户能力状态至少包括已确认具备、很可能具备、曾计划但结果未知、正在建设、能力不足、明确缺失和无法判断。
- 中标、签约、投产、维保和现有供应商优先形成能力基线；历史招标只能证明曾计划。
- 目标能力来自行业 Skill、有效政策、用户研究目标和我方产品能力，并保留来源；我方产品能力不得反向证明客户存在需求。
- 商机必须包含未满足能力缺口；只有缺口、没有触发和窗口时裁决不得高于 G2。

#### FR-OIG-005 政策适用性

- 政策至少区分 DRAFT、PUBLISHED、EFFECTIVE、TRANSITION、ENFORCEMENT、SUPERSEDED、EXPIRED 和 UNKNOWN。
- 识别发布机构、适用主体、强制/鼓励/禁止要求、生效与整改期限、监督处罚和被替代文件。
- 只有政策适用于目标客户、已生效或进入整改、客户存在能力缺口且产品可覆盖时，才能形成较强政策驱动。
- 征求意见稿、泛指导意见、行业倡议和领导讲话具有不同裁决上限，不能直接证明客户必须采购。

#### FR-OIG-006 反证优先与硬门槛

- Gate 前强制检查需求是否已满足、采购是否完成、现供应商与合同锁定、时间/主体冲突、不采购/延期/自研可能及我方资格。
- G5 必须同时满足主体、时间、未满足缺口、当前触发/窗口、候选产品、直接 Claim、主要反证处理和无硬性阻断。
- 反证未处理、只有单一证据或单一分析维度时不得输出 G5。
- OIG 未完成或执行失败时，只能输出“商机裁决未完成”，不得回退旧 `opportunity_score`。

#### FR-OIG-007 裁决后评分

- 新评分器只读取 GateDecision 及其去重因子，不直接对原始 Evidence 集合生成商机等级。
- 评分用于同一裁决等级内排序，不得以高分越过硬门槛或提升销售阶段。
- 初始维度包括缺口、触发、合同/介入窗口、政策强度、产品适配、竞争可胜、交付资质和证据完整度；权重版本化并通过试点校准。
- 单条证据在一次决策中使用 `dedupe_key` 确定主作用，禁止同时在缺口、窗口、政策和适配中重复加分。

#### FR-OIG-008 商机裁决卡与行动约束

- 报告第一屏展示分析截止日期、裁决等级、商机类型、客户已有能力、未满足缺口、窗口、支持/反向证据、硬阻断和下一验证事项。
- 提供客户事件时间线、能力地图、采购与合同窗口、政策影响和假设排行。
- 行动依次从公开补证、内部关系核验、客户验证、技术交流、方案验证到 POC/投标逐级推进。
- 窗口未确认时不得生成“立即参与招标”等确定性行动；没有内部能力依据时不得生成 Why Us。

### 12.7 验收标准

- 只输入企业名称并选择能力档案即可创建任务。
- 系统可自动选择 1～3 个候选产品并说明理由。
- 公开信号只生成商机假设，不会自动创建正式商机。
- 已截止招标误判为开放窗口率为 0%；已中标/投产误判为从零建设需求率为 0%。
- 每个高等级候选通过全部 OIG 硬门槛，关键因子 Claim 覆盖率 100%，单证据重复加分率 0%。
- 报告第一屏展示 GateDecision、分析截止日期、事件时间线、客户能力基线、缺口、窗口和主要反证。
- 三年期服务合同能够生成带依据和置信度的预计续约窗口，但不会伪造确定到期日。
- 只有战略讲话、泛指导政策或单一分析维度时，裁决不高于 G2。
- 需求结论来自外部或客户私有证据，产品能力来自内部知识，三个证据域不会混用。
- 硬性阻断命中时直接降级，不会被其他维度高分抵消。
- 推荐结果同时展示得分、证据置信度、信息完整度和主要正负因素。
- v3.4 可维护利益相关者、资格卡、竞争作战卡、价值假设和正式阶段记录。
- 所有客户确认状态和商机阶段提升都有用户操作记录。
- 不存在合适产品时不会生成虚假的强推荐。

## 13. 客户雷达与业务反馈（v3.5）

### 13.1 客户雷达

#### FR-WATCH-001 订阅目标企业

- 生成“变化摘要”，不重复生成完整报告。
- 重大变化可触发报告补充研究草案。

### 13.2 业务结果反馈

#### FR-FBK-001 结果标签

用户可以标记：

- Signal 有效或无效。
- 商机假设已接受、拒绝、暂缓或过期。
- 客户已验证或验证失败。
- 已转正式商机。
- 进入方案塑造、投标/采购、成交或丢单。
- 暂不投资、继续现状、选择竞品或客户自研。

#### FR-FBK-002 质量学习

- 反馈用于 Skill 和评分模型评测。
- 不允许直接在线自动修改生产 Skill。

### 13.3 经营 Dashboard

面向销售经理展示：

- 研究客户、Signal、商机假设、销售接受、客户验证、正式商机、方案/投标、赢单/丢单漏斗。
- 各阶段转化率、平均停留时间和超期对象。
- 首次洞察时间、售前研究节省工时、单个有效商机综合成本。
- 已由销售或 CRM 确认的正式商机金额、赢单金额和阶段加权金额。
- Skill、产品、行业和证据来源维度的采纳率与推进率。

系统不得把 AI 推测金额计入真实商机金额。金额缺失时展示“未录入”，不得用行业均值自动补齐。

## 14. AI 与智能体设计

### 14.1 新增或升级的智能体

| 智能体 | 职责 |
| --- | --- |
| IntentRouter | 判断解释、补充研究或修订意图 |
| ClarificationCoordinator | 在执行前和执行中识别重大不确定性，生成最少必要问题并协调暂停、回答与恢复；不输出隐藏思维链 |
| ContextBuilder | 从报告、Claim、三类证据、搜索结果和内部知识构建最小充分上下文 |
| ContextCompactor | 按有效预算生成带来源的结构化 ContextSnapshot，并支持从原始资产回填；不覆盖或删除原始记录 |
| RetrievalRouter | 按问题意图选择结构化、全文或向量检索，并执行数据域和模型路由策略 |
| ReportQAAgent | 基于现有资产回答报告问题 |
| FollowUpResearchAgent | 将追问转化为受控子研究任务 |
| ReportEditorAgent | 生成带证据的报告修改草案 |
| EntityResolutionAgent | 生成目标企业候选和置信度 |
| SkillRouter | 选择一级 Skill 和必要子 Skill |
| SkillCompiler | 将标准 Skill 编译为耐久 WorkUnit DAG、Agent 输入契约和 EvidencePolicy；不编译为旧任务级 Harness 状态机 |
| CapabilityExtractionAgent | 从内部资料抽取产品、案例、资质和限制 |
| ProductMatcherAgent | 匹配客户需求与我方产品 |
| TemporalNormalizer | 以 analysis_as_of_date 归一化发布、事件、截止、政策和合同时间；确定性规则优先 |
| ProcurementLifecycleAgent | 分类采购性质并识别 PLANNED 到 LIVE/MAINTAINING/EXPIRED 等状态 |

### 14.2 智能体控制原则

- 智能体只能使用明确授权的工具。
- 解释模式禁止调用搜索工具。
- 补充研究必须创建独立运行记录。
- 报告编辑智能体只能生成草案。
- 内部知识不得出现在外部搜索 Query 中。
- 客户私有证据不得出现在外部搜索 Query 中，也不得进入未获批模型路由。
- 公开资料研究可使用经配置批准的云端模型验证能力上限；本地或私有模型作为敏感数据和私有化部署底线。任何路由切换都必须遵守数据域策略，而不是只按模型效果选择。
- 模型评测应先验证工作流、Prompt 和工具设计，再比较云端与本地模型的质量、成本和延迟；模型蒸馏不属于本 PRD 的必做范围。
- Skill 指令不能覆盖系统安全策略和用户权限。
- Prompt Injection 内容只能作为不可信数据，不能作为系统指令执行。
- 所有智能体调用记录模型、Prompt 版本、输入资产 ID、输出、Token 和耗时。
- UI 只能展示操作状态、工具结果和经整理的决策摘要，不展示隐藏思维链。
- 智能体不得把会实质改变结论的未知信息当作默认事实；必须发起澄清，或由用户明确授权按已展示的假设继续。
- 长上下文模型不得成为整包输入的理由；所有智能体统一通过 ContextBuilder 获取分层上下文，并记录预算、选择、压缩和回填清单。
- OIG 必须在商机评分和正式报告生成前完成；Gate 失败不得回退旧 `OpportunityScorer`、旧分数或无裁决报告。
- 时间、期限、状态转换、重复加分和硬门槛优先使用确定性规则；LLM 负责语义抽取、候选假设和反证发现，不能覆盖规则结果。
- Agent 不拥有 Task 全局状态；所有暂停、恢复、取消、等待输入和终态转换均经过 execution 状态机与命令服务。
- 每个外部调用必须在物理请求前创建持久账本记录，绑定调用幂等键、Provider、模型、WorkUnit、网络截止和输出上限。
- 候选筛选 G1 未通过期间仅允许影子运行，任何影子输出都不得进入 Evidence、Claim、OIG、报告或用户可见推荐。
- `PARTIAL` 必须通过 Skill 最低交付物和强制审计门，不能把技术失败包装成部分成功。

### 14.3 Human-in-the-loop 节点

以下情况必须等待用户：

- 中低置信度企业消歧。
- 内部资料结构化抽取发布。
- 客户私有材料的敏感级别、授权范围和 Claim 确认。
- 商机假设的接受、拒绝和转正式商机。
- 利益相关者真实性、客户确认状态和资格阶段提升。
- 下一步行动进入待执行状态以及对外导出/Webhook 调用。
- 外部 Skill 导入和发布。
- 报告草案正式写入。
- 高风险或预计费用显著增加的补充研究在创建前确认；运行中的 Token/费用超额只告警，不作为自动暂停理由。
- 相互冲突的报告草案合并。
- 执行前或执行中出现会影响主体、范围、关键事实、产品选择、数据授权或报告质量的重大不确定性。

### 15.9 关键关系规则

- Task 从创建时即必须绑定非空 `target_account_id`；系统不存在按名称猜测、首次打开补绑定或历史空值回填路径。
- 线索发现模式 Task 绑定一个 `capability_profile_id`。
- Task 可绑定多个产品候选，但正式推荐必须记录产品版本。
- Signal 必须绑定至少一个支持 Claim；商机假设必须绑定 Signal、支持/反向 Claim 和下一验证动作。
- Signal 和商机假设必须引用当前有效 GateDecision；G0/G1/GX 不得创建待销售接受假设，G2/G3 只能创建补证或低置信度验证假设。
- OIG 裁决等级不替代 SalesAccepted、CustomerValidated 和 Opportunity 销售阶段；机器不得自动提升人工业务阶段。
- 商机假设只能由用户标记 SalesAccepted；正式 Opportunity 只能在阶段门通过后由用户创建。
- Report、对话、产品匹配和商机对象引用同一 Claim Registry，不重复维护相互独立的结论文本。
- ReportVersion 必须绑定生成它的 ResearchRun、SkillVersion 和产品版本。
- SkillVersion、ProductVersion、ReportVersion 均不可原地覆盖。
- TargetAccount、CapabilityProfile、Skill、Claim、Report 和 Opportunity 均归属于 Workspace。

## 16. API 能力分组建议

以下为产品级接口分组，不规定最终路径细节。

### 16.1 Workspace

- 获取默认 Workspace。
- 查询 Workspace 基础信息和成员角色。
- 查询 Workspace 模型与数据域策略。

### 16.2 目标企业

- 创建/更新目标企业。
- 发起消歧。
- 获取候选。
- 确认候选。
- 获取集团关系。

### 16.3 Opportunity Intelligence Gate

- 查询分析截止日期、时间归一化状态和时间冲突。
- 查询采购项目、事件时间线、采购性质与生命周期。
- 查询合同、预计窗口、推断依据和现有供应商。
- 查询客户能力基线、目标能力和缺口。
- 查询政策适用性、生命周期、义务和能力映射。
- 创建或重新计算不可变 GateDecision。
- 查询 G0～G5/GX、硬门槛、主要正负因子、缺失层、评分版本和重验条件。
- 查询商机裁决卡；OIG 失败时返回明确错误，不返回旧评分。

### 16.4 商机作战

- 查询和确认 Signal、Claim 及冲突状态。
- 创建、接受、拒绝、暂缓和重新验证商机假设。
- 创建正式商机并记录阶段变化。
- 维护利益相关者、资格卡、竞争作战卡和价值假设。
- 创建、分配、完成下一步行动。
- 导出 CSV/JSON 和触发经确认的 Webhook。

### 16.5 报告工作台

- 创建/查询会话。
- 流式发送消息。
- 创建补充研究。
- 查询研究进度。
- 查询待澄清请求、提交回答、选择推荐假设或取消任务。
- 从澄清关联的 Run/StageRun 和 `control_version` 幂等恢复运行，并查询恢复结果。
- 查询本次 ContextManifest、ContextSnapshot、Token 分配及其原始来源。
- 按权限从原始资产回填上下文；回填不改变历史压缩快照。
- 生成报告草案。
- 获取 Diff。
- 接受/部分接受/拒绝草案。
- 查询和导出报告版本。
- 上传和管理客户私有材料。
- 获取 30 秒摘要、一页简报、商机卡和其他业务视图。

### 16.6 Skill

- 创建 Skill。
- 获取/更新 Skill 文件。
- 编译、校验和试运行。
- 管理父子依赖。
- v3.5 导入 GitHub/离线 Skill。
- 查询上游更新。
- 运行评测。
- 发布/废弃/归档。

### 16.7 企业能力

- 能力档案 CRUD。
- 产品、方案、案例和资质 CRUD。
- 文档上传、解析、抽取和确认。
- 混合检索。
- 产品匹配预览。

### 16.8 批量模板

- 获取模板列表。
- 下载模板。
- 上传预览。
- 映射和验证。
- Dry Run。
- 创建批次。
- 下载错误行。

### 16.9 耐久任务执行

- 查询 `desired_state`、`observed_state`、当前 Run、阶段、批次、剩余工作、最近持久点、恢复次数和 ETA 区间。
- 提交幂等 pause/resume/cancel 命令；非法状态转换返回 409，跨 Workspace 或非所有者统一隐藏资源。
- 通过 SSE 按 `after_sequence` / `Last-Event-ID` 获取 TaskEvent；断线后补历史并按 sequence 去重。
- 查询费用/Token 告警、外部调用审计和 PARTIAL 缺口；不向普通用户暴露 Prompt 原文、访问令牌或隐藏思维链。
- 生产接口不再提供旧 Harness 状态、Redis Checkpoint 或旧任务 WebSocket 作为第二事实源。

## 17. 非功能需求

### 17.1 性能

| 指标 | 目标 |
| --- | --- |
| 普通列表/详情 API | P95 ≤ 800ms，不含外部服务 |
| 会话上下文检索 | P95 ≤ 2s；包含预算计算、相关资产选择和已有快照读取，不含首次异步压缩 |
| 解释模式首个状态反馈 | ≤ 1s |
| 解释模式首 Token | P95 ≤ 5s，模型可用情况下 |
| 1000 行批量文件预览 | ≤ 15s |
| Skill 编译 | ≤ 10s，不含评测 |
| 文档上传确认响应 | ≤ 2s，解析异步执行 |
| 标准四维研究任务 | 第一阶段 P90 ≤ 40min；候选筛选通过 G1 并正式启用后，稳定目标 P90 ≤ 20min |
| 任务控制受理 | pause/resume/cancel P95 ≤ 2s；受理不等于正在进行的外部调用已被强杀 |
| 安全暂停 | P95 ≤ 120s，或不晚于当前外部调用硬截止；进入 PAUSED 后新增外部调用为 0 |
| 恢复有效工作 | resume 受理 P95 ≤ 2s；恢复后首个有效 WorkUnit P95 ≤ 10s |
| Outbox 投递 | 正常 P95 ≤ 2s；通知丢失时轮询兜底 ≤ 5s |

外部搜索、抓取和 LLM 耗时不纳入同步 API SLA，但必须受物理网络截止约束并持续返回已持久化阶段状态。2026-07-19 的 20/50 任务压测结果只证明当前开发环境耐久执行可运行，不替代标准业务任务质量与稳定目标验收；抓取批次拆分和增益早停调度未完成端到端验收前，上表的研究任务时长均不得作为已实现承诺。

### 17.2 容量建议

- 批量任务上限：1000 行，可配置。
- 单文档上限：50MB，可配置。
- 单能力档案默认存储配额：2GB，可配置。
- 单会话的精确工作集按有效 Token 预算、相关性和当前任务阶段选择，不以固定 50 轮作为质量保证；可以将 50 轮设为产品上限，但不得挤出 L0 固定上下文和关键反证。
- 早期内容通过带来源的结构化 ContextSnapshot 参与检索；原始消息和研究资产按保留策略存储，不因压缩提前删除。
- 单次回答上下文预算由统一 ContextBudgetManager 与 TokenTracker 共同控制，并预留输出、工具和安全余量。
- ContextSnapshot 生成可以异步执行；首次回答若快照尚未就绪，应从原始资产构建较小工作集，不得使用无来源的临时摘要。

### 17.3 可靠性

- 外部研究任务按可重入短 WorkUnit 执行，恢复只读取 PostgreSQL 已完成单元、游标和资产，不依赖 Redis-only Checkpoint。
- Worker 在资产提交后、消息 ack 前崩溃时，重投必须识别单元已完成并直接确认，不重复 Evidence、Report、Audit 或费用结算。
- 使用 `lease_epoch` fencing 阻止旧 Worker 在新租约产生后发起调用或提交结果；Redis 清空后可由 Outbox 与恢复对账器重建待执行工作。
- `COMPLETED` 只能在报告、引用关系和强制审计全部持久化后写入；`PARTIAL` 必须满足 Skill 最低交付物。
- OIG 必须作为报告阶段的显式前置 WorkUnit；Gate 失败、超时或裁决不完整时不得继续旧评分或确定性商机报告。
- 会话消息先落库后推理，避免断线丢失。
- 报告草案生成失败不影响正式版本。
- 文档解析失败可单独重试。
- Skill 编译和评测失败不影响已发布版本。

### 17.4 安全

- 外部 URL 遵循现有 SSRF、重定向和域名策略。
- 上传文件执行 MIME、扩展名、大小、病毒和压缩安全检查。
- v3.5 GitHub 导入固定 Commit SHA，禁止导入后内容漂移。
- 外部 Skill 代码不执行。
- 内部知识不发送给 Search Provider。
- 客户私有证据不发送给 Search Provider。
- 核心业务数据按 `workspace_id` 隔离，个人操作按 `user_id` 审计。
- 客户私有和内部敏感内容只允许进入 Workspace 已批准的模型路由；未经批准不得回退到公共云模型。
- Provider Key 继续加密存储。
- 敏感操作写入审计日志。
- 防止 Skill、网页和内部文档中的 Prompt Injection 提升权限。

### 17.5 隐私和数据治理

- 用户可分别配置研究资产、报告、客户私有材料、内部文档和会话的保留期。
- 删除能力档案时展示受影响的任务和报告。
- 对历史审计必须保留引用对象的不可变快照或哈希。
- 支持导出 Workspace 自己的客户、商机、能力档案、Skill 和报告数据。
- 客户私有材料的导出、模型调用和 Webhook 发送必须执行敏感级别与授权范围检查。

### 17.6 成本治理

- 解释模式默认不搜索，优先低成本模型。
- 补充研究执行前展示预计成本；明显增加费用或扩大范围时可要求用户在创建 Run 前确认。
- 线索发现模式按产品候选数、Skill 数量和深度估算成本。
- 每个任务、会话和能力档案支持费用与 Token 告警阈值，并通过不可变账本记录预留、结算、退还和未知计费结果。
- 80%/95%/100% 只产生分级提示和审计；不得在运行中自动暂停、取消、减少强制 Evidence/Claim/OIG 审计或切换到未获批低质量模型。
- 物理上下文上限、网络截止、权限和数据域策略仍是硬约束；它们与费用告警必须使用不同原因码，不能混为“预算不足”。

### 17.7 可观测性

- 记录 workspace/account/hypothesis/opportunity/task/run/stage/unit/agent/model/provider/skill/version/product/report_version 维度的日志和指标。
- 关键链路支持 Trace ID。
- 区分用户错误、数据不足、Provider 故障、系统故障和安全阻断。
- 可统计各 Skill 的触发率、成功率、成本和采纳率。
- 持续统计候选漏斗、批次数、信息增益、外部调用、P50/P90/P99、租约恢复、重复副作用、Outbox 延迟、预算账本和 SSE 重连。

## 18. 产品指标

### 18.1 北极星指标

> 由系统发现或增强、经销售接受，并在规定周期内完成至少一次有效阶段推进的证据化商机数。

阶段推进包括：完成客户验证、转正式商机、进入方案塑造、进入投标/采购或成交。单纯生成报告、Claim 或商机假设不计入北极星指标。

```text
研究客户数
→ 有效需求信号数

→ 销售接受数
→ 客户验证数
→ 正式商机数

→ 成交数
```

### 20.11 安全与权限

建议至少覆盖：

- Workspace A 无法读取 Workspace B 的客户、商机、能力档案、文档、会话和报告。
- 内部文档内容不会出现在 Search Provider 请求日志中。
- 客户私有材料不会出现在 Search Provider 请求、未获批模型输入或未经确认的 Webhook 中。
- 外部网页中的恶意提示不会改变智能体权限。
- GitHub Skill 的软链接、路径穿越和压缩炸弹被阻断。
- 删除档案、报告和 Skill 的操作进入审计日志。

### 20.12 耐久执行与长任务

| 边缘情况 | 预期行为 | 建议测试 |
| --- | --- | --- |
| Worker 在资产提交后、消息 ack 前崩溃 | 重投识别 WorkUnit 已完成并直接确认，不重复业务副作用 | 在事务提交后注入 kill |

| Redis 队列和事件缓存清空 | PostgreSQL Outbox/对账器重新投递未完成单元，已完成单元不重做 | 执行中清空隔离 Redis |
| Outbox NOTIFY 丢失 | 轮询在 5 秒内补投且只投一次 | 禁用通知后保留未发布行 |
| Provider 返回 `finish_reason=length` 但 JSON 完整 | 结构校验通过则接受；正文截断或 Schema 不完整才失败 | 构造完整与截断两个响应 |
| 暂停发生在外部调用中 | 显示 PAUSING，等待硬截止或调用结束；之后不创建新调用 | 慢模型调用中提交 pause |
| 重复 pause/resume/cancel | 相同幂等键返回首次结果；不同命令按 control_version 决定 | 并发提交重复控制命令 |
| 强制审计失败但已有部分正文 | 只有满足 Skill 最低交付物才为 PARTIAL，否则 FAILED | 模拟模型审计与持久化失败 |
| 候选筛选影子结果与基线不同 | 用户输入、抓取、Evidence、OIG 和报告保持基线路径不变 | 开启影子并注入相反 Top20 |
| 费用达到 100% 告警 | 记录告警和账本，继续执行必要质量步骤，不自动换低质模型 | 设置很低告警阈值 |

## 21. 绿色数据库基线与后续迁移策略

### 21.1 首次上线基线

- `backend/migrations/versions/001_greenfield_baseline.py` 是首次上线唯一根迁移，直接创建当前 ORM 的 80 张业务表。
- 旧 001～025 开发迁移不再参与运行；基线不包含历史回填、旧字段别名、旧 Skill JSON 种子或双结构兼容。
- Workspace、TargetAccount、耐久执行、研究/报告、三证据域、Claim、OIG、能力中心、批量、商机假设和行动从首次写入即使用最终字段和约束。
- 所有环境只允许 Alembic 创建 Schema；FastAPI 启动和种子初始化不得调用 `Base.metadata.create_all()`。

### 21.2 基线验收

独立、名称含 `test` 的空 PostgreSQL 数据库必须执行：

```text
upgrade head
→ alembic check（与 ORM 零差异）
→ downgrade base
→ 无业务表和 PostgreSQL Enum 残留
→ 再次 upgrade head
→ alembic check
```

循环外键必须在表创建后显式建立；`taskstatus`、`loglevel`、`batchstatus` 等独立 Enum 必须在开发期 downgrade 时显式删除。

### 21.3 首次上线后的迁移

- 首次生产部署并产生正式业务数据前，Skill V2、售前作战、Watchlist/反馈等所有 Schema 变更都直接更新 ORM 并重新生成/校验唯一绿色基线 001；不得创建开发期 002～004。
- 首次产生正式业务数据后，才从 002 起为实际发生的第一个生产后变更连续编号；不提前把编号绑定到尚未完成的产品模块。
- 每个后续迁移必须包含约束测试、空库全链升级、带当前生产版本数据的升级演练、ORM 零漂移和开发期 downgrade 验证。
- 生产回滚使用备份恢复或前向修复，不把 Alembic downgrade 当作有业务数据后的默认回滚手段。
- 不为已删除的开发迁移、旧 Skill 格式、旧 Task 字段或旧执行引擎编写兼容分支。

### 21.4 系统种子与业务数据

- 数据库迁移只负责 Schema，不写管理员、Provider、Skill 或示例业务数据。
- 默认管理员与搜索 Provider 由迁移成功后的幂等初始化服务创建。
- 标准内置 Skill 以仓库中的 `SKILL.md` 目录为唯一来源；不得把旧 `expert_skills.config_yaml` 种子重新加入迁移。
- 产品、客户、报告、Claim 与商机假设均由用户/API 正常创建，不提供虚构的首次上线示例数据。

## 22. 风险、依赖与缓解措施

| 风险 | 影响 | 缓解措施 |
| --- | --- | --- |
| 当前 v3.1 未完全验收 | 新功能叠加不稳定 | P0 作为版本准入门槛 |
| 耐久执行开发完成但首次部署未验收 | 未验证的部署顺序或配置导致上线失败 | TEO-Release 独立阻断门、空库建库、健康检查和单路径烟测 |
| 候选筛选机器门失败却提前启用 | 为提速牺牲召回并污染 Claim/OIG | 生产默认关闭；10 样本/50 影子任务/30 天触发重评，机器 G1 通过后再授权 |
| 旧 Harness/Redis Checkpoint 死代码被重新接入 | 重复执行、恢复漂移和双状态源 | 冻结旧入口、删除不可达分支、代码扫描和路由契约测试 |
| 澄清只实现状态、未实现持久问题/回答 | WAITING_FOR_INPUT 后无法安全恢复 | v3.2 补齐 ClarificationRequest/Response、control_version 和零调用等待测试 |
| WorkUnit 边界过粗 | 单次调用过长，暂停慢且重试成本高 | 网络硬截止、批次化、稳定 unit_key、P99 反推租约和负载指标 |
| 预算告警被错误实现为质量熔断 | 报告缺关键证据或审计 | 账本只告警；强制质量门不降级；费用确认只发生在新 Run 创建前 |
| 同时建设多个平台级模块 | 范围失控、业务价值延迟 | 按 v3.2～v3.5 纵向场景递进，每版设置继续/停止门槛 |
| 报告上下文过大或无差别整包输入 | 成本和延迟上升、注意力稀释、回答漂移 | L0～L3 分层、ContextBudgetManager、结构化快照、原始资产回填和压缩质量门 |
| 上下文压缩丢失反证或用户确认 | 报告结论偏移且难以审计 | 关键内容禁止生成式压缩、条目来源 100%、黄金集盲评、从原始资产重建 |
| Skill 自由度过高 | 执行不可控 | 编译 Schema、工具白名单、发布评测 |
| 外部 Skill 恶意内容 | 数据和权限风险 | 固定 Commit、静态检查、隔离、禁止代码 |
| 文档解析质量不稳定 | 产品卡错误 | 用户校对后发布、保留原文位置 |
| 线索发现模式强行匹配产品 | 产生虚假商机 | 硬门槛、反证、允许“无明确机会” |
| Signal 被包装成正式商机 | 销售信任下降、漏斗失真 | 独立商机假设对象、阶段门、用户确认和有效期 |
| 历史招标被判断为当前开放机会 | 销售采取错误行动并损害客户信任 | analysis_as_of_date、采购生命周期、截止规则和 OIG 黄金集 |
| 已中标/投产能力被判断为缺失 | 重复推荐客户已有系统 | 客户能力基线、采购结果串联和 baseline 证据作用 |
| 泛政策被放大为强制采购 | 形成虚假政策商机 | 政策生命周期、适用主体、义务强度、整改期限和能力缺口联合判断 |
| OIG 失败后回退旧分 | 错误逻辑继续静默进入报告 | 禁止回退；报告标记裁决未完成并阻断正式商机结论 |
| 机器裁决等级与销售阶段混用 | 系统自动制造客户确认或正式商机 | G0～G5/GX 与 SalesAccepted/CustomerValidated/Opportunity 分离 |
| 销售不维护验证结果 | 无法形成经营闭环和校准数据 | NextBestAction、低成本反馈入口、试点运营责任人 |
| 同名企业识别错误 | 整份报告失真 | 候选确认、置信度和主体关系标注 |
| 内部知识泄露 | 严重安全风险 | 搜索隔离、权限、审计、最小上下文 |
| 客户私有证据泄露 | 客户信任和合规风险 | 独立证据域、授权范围、敏感级别、模型路由和导出审计 |
| AI 编造 ROI 或商机金额 | 管理决策失真 | 只生成计算模型；金额必须来自销售、客户或 CRM 确认 |
| 版本数量快速增长 | 存储和管理复杂 | 归档、保留策略、不可变快照 |
| 评测成本高 | Skill 迭代慢 | 分层评测、Mock/小模型预检、正式模型复测 |

### 22.1 外部依赖

- 稳定的 LLM Provider 和模型路由。
- 搜索 Provider 和网页抓取能力。
- 文档解析/OCR 组件。
- 文件存储和备份策略。
- 向量检索或等价的混合检索能力。
- v3.5 GitHub 仓库读取能力和网络安全策略。
- 试点销售、售前和行业专家提供基准样本、客户验证结果和人工耗时数据。
- 若启用 Webhook/CRM 输出，需明确目标系统字段契约和安全策略。

### 22.2 最大落地阻力判断

短期最大的工程阻力是把已经完成隔离验证的唯一耐久执行路径完整部署到空白生产环境，并让 v3.2 澄清、上下文和 OIG 直接复用 WorkUnit/TaskEvent，而不是重新在 Agent 内构造第二套状态。长期最大的产品技术阻力仍是把异构、冲突且会过期的网页与客户材料稳定转成可复用的 Claim 和售前业务对象：

1. **Claim 结构化与实体归属**：同一事实的主体、时间、支持/反向证据、真实性状态和有效期必须保持一致，否则报告、产品匹配和商机判断会相互矛盾。
2. **客户私有文档解析与安全路由**：RFP、会议纪要、表格和扫描件结构差异大，同时对权限、模型路由和引用位置要求最高。
3. **业务验证反馈的持续采集**：如果销售不记录接受、客户验证和行动结果，再好的智能体也无法校准商机判断。

耐久 execution 域已有工程基础，但当前首次生产部署验收仍为 No-Go，候选筛选机器门也未通过。完成单路径部署后，Claim/文档结构化、执行中澄清、OIG 与业务反馈不能靠兼容分支或简单回退规避，因此应作为 v3.2 试点的最高风险项。

## 23. 专家评审重点

两位专家首轮意见已按 0.6 节处理。下一轮评审不再重复判断“是否需要从报告走向商机闭环”，而应重点验证以下落地边界：

### 23.1 产品与业务

1. Signal、Claim、商机假设、客户验证和正式商机的边界是否足够明确。
2. v3.2 的商机假设卡与 NextBestAction 是否能被试点销售实际使用和维护。
3. 可配置资格卡、利益相关者地图、竞争作战卡和价值假设是否覆盖目标行业的真实打单过程。
4. 产品匹配的硬门槛、加权评分和置信度校准是否适合试点产品。
5. “暂无明确机会”“继续现状”“延期”和“客户自研”是否被正确视为合法判断。

### 23.2 AI 与 Skill

1. v3.3 一个一级 Skill + 3～5 个二级 Skill 是否足以验证专家策略价值。
2. `SKILL.md` 与编译后执行规范的边界及 Dry Run 展示是否清晰。
3. 外部 Skill 长期禁止执行代码是否满足安全要求。
4. Skill 黄金用例、专家盲评和业务推进指标是否足以防止质量退化。
5. 三证据域、Claim 冲突、有效期和反证机制是否完备。
6. 模型路由是否同时兼顾云端能力验证、本地部署和客户私有数据安全。

### 23.3 数据与架构

1. Workspace 作为业务资产归属是否足够，且未过度引入复杂多租户。
2. Claim、报告、Skill、产品和商机阶段的版本及审计模型是否完整。
3. 首次部署前持续收敛的唯一绿色基线 001、ORM 零漂移，以及正式数据产生后才启用 002 起前向迁移的策略是否完整。
4. Clarification、ContextSnapshot 和 OIG 能否作为短 WorkUnit 接入且保持 TaskEvent、幂等与暂停语义。
5. 结构化精确匹配 + 全文/向量路由是否足够，是否确有引入图数据库的证据。
6. 商机作战对象数量是否会造成前端和数据模型过载。

### 23.4 安全与合规

1. 客户私有证据的授权、敏感级别、模型路由、导出和删除策略是否充分。
2. 内部文档发送给第三方 LLM 的边界和审计要求。
3. v3.5 GitHub Skill 导入的威胁模型是否充分。
4. 案例、资质、内部价格、商机金额和客户材料的导出控制。
5. 数据删除与历史审计之间的冲突处理。

### 23.5 测试与交付

1. 各版本验收口径是否可自动化。
2. 是否需要建立行业专家盲评集。
3. 性能和容量目标是否符合实际部署环境。
4. P0 试点准备及 v3.2～v3.5 纵向拆分是否合理。
5. 每个版本的继续、调整和停止条件是否可量化。

## 25. 附录：关键术语

| 术语 | 定义 |
| --- | --- |
| Workspace | 客户、商机、能力档案、Skill、报告等业务资产的基础归属边界；初期每个账号拥有一个默认 Workspace |
| Durable Execution | 以 PostgreSQL 为事实源，将长任务拆为可重入短 WorkUnit，并通过状态机、租约、事件和 Outbox 支持暂停、恢复和审计的执行架构 |
| WorkUnit | 具有稳定 unit_key、输入哈希、依赖、截止、尝试和资产引用的最小可重入执行单元 |
| TaskRun / StageRun | 任务一次执行 generation 及其阶段单元的持久记录，作为恢复、进度和审计依据 |
| PARTIAL | 因外部依赖或范围不足只交付部分结果的明确终态；仅在 Skill 最低交付物和强制审计均满足时成立 |
| G1 候选筛选门 | 候选筛选的机器质量门；当前 `MANUAL_CONDITIONAL_PASS` 只允许开发和影子验证，不等于 G1 通过 |
| 研究资产 | 搜索词、搜索结果、网页快照、证据、评估、反思等可复用研究过程数据 |
| 外部证据 | 来自目标企业、政府、招标平台、媒体等公开来源的事实依据 |
| 客户私有证据 | 经授权录入的客户访谈、会议纪要、RFP、邮件、CRM 备注和现场调研等非公开材料 |
| 内部知识 | 用户上传的我方产品、方案、案例、资质和能力资料 |
| Signal | 由证据支持的客户事件或需求信号，本身不等于商机 |
| Claim | 可被多个报告和业务对象复用、带支持/反向证据、真实性状态和有效期的关键结论 |
| 商机假设 | 基于 Signal、Claim 和我方能力形成、等待销售接受及客户验证的机会判断 |
| Opportunity Intelligence Gate | 位于证据审计之后、评分和报告之前的商机裁决层，综合时间、能力、缺口、触发、窗口和适配 |
| GateDecision | 在指定 analysis_as_of_date 下生成的不可变机器裁决快照，不等于人工销售阶段 |
| 商机裁决等级 | G0～G5/GX，用于区分无关、历史能力、待验证缺口、当前信号、潜在窗口、可介入候选和暂无商机 |
| 客户能力基线 | 根据中标、合同、投产、维保等证据形成的客户当前能力状态 |
| analysis_as_of_date | 本次研究和裁决使用的固定分析截止日期，用于时间判断和历史回放 |
| 正式商机 | 通过配置的阶段门并由用户确认创建的销售机会 |
| NextBestAction | 带目标、角色、证据、负责人、计划日期和结果的结构化下一步验证行动 |
| CompetitiveBattlecard | 针对竞品、现有供应商、自研、维持现状或延期等竞争选择形成的结构化作战卡 |
| 报告草案 | 尚未被用户确认、不能替代正式报告的修改结果 |
| 报告版本 | 用户确认后的不可变正式报告快照 |
| 一级 Skill | 面向完整业务场景、负责编排多个子 Skill 的策略 Skill |
| 二级 Skill | 负责单一专业研究能力、可被多个一级 Skill 复用的原子 Skill |
| Skill 编译 | 将 `SKILL.md` 和引用文件转换为 WorkUnit DAG、Agent 输入契约和证据策略的过程 |
| 企业能力档案 | 表示某个企业、品牌或业务单元的产品与方案能力集合 |
| 产品匹配 | 将目标客户外部需求信号与我方产品能力、限制和案例进行对照 |
| 消歧 | 确认用户输入的企业名称具体指向哪个真实企业主体 |
| 线索发现模式 | 仅输入目标企业并选择能力档案，由系统自动发现 Signal、选择候选产品和 Skill、生成待验证商机假设的模式 |
